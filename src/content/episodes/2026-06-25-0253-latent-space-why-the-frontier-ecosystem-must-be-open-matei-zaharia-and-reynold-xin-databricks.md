## 从开发者痛点到统一接口

**Matei Zaharia**

内部有两类实践在推动我们：一类是 coding agent，开发团队自己做了很多 wrapper、Codex 和云端工具；另一类是 data science agent，比如我们研究团队自己做的 Genie。

这两类工具都要求频繁切模型、切 harness，而且用户想协作、共享上下文。没有会话共享和检索层，代理很难真正用于协作。

所以一开始大家都觉得我把 coding agent 和 custom agent 放在一起很奇怪，但本质问题一样：要提供可交付、可控、可移植的代理基础设施。

我觉得这和操作系统很像，协议层和通信机制的作用会特别关键。

我们团队做过 open sharing，把公司的关键表实时共享给供应商，比如库存、销售情况，避免一堆邮件、Excel 或电话同步。

有人会问有了 vibe coding 就不需要设计协议和 API 了吗？我不认同。

当多个团队、多个合作方共同工作时，仍然需要稳定的互操作层来协调，今天这期正是围绕这个。

## 云沙盒、分享与安全策略

**Swyx**

再讲一下你们的沙盒。你们提到既要快，也要可用。

**Matei Zaharia**

我们早期就发现团队最需要的是稳定会话，不要每次启动都等很久。特别是做代码调试时，本地依赖和环境恢复成本很高。

Neon 的思路很有启发：状态和计算分离，但对数据库工作流还是要保留持久层和本地能力，比如会话里的库和文件。

**Reynold Xin**

我们在内部看到，按规模跑下来每天 50 到 60 百万台虚拟机很常见，数据库启动和分支实验增长很快，开源的接口能帮助这些规模下更快扩展。

**Matei Zaharia**

安全和支出管理是另一个关键点。传统权限是二元放行，但代理场景需要上下文感知策略：同一会话里风险会随行为累积。

如果一次操作出现风险，比如安装可疑 NPM 包或读取大量机密文档，后续动作应该更严格。反之也可以放宽。

这是典型的 stateful policy。我们会追踪会话上下文，再结合事件语义做允许、阻断或确认。

**Reynold Xin**

另外我们还把低层工具事件映射到高层语义，这样 policy 能针对“动作类型”决策，而不是只看裸 API 调用。

Panther 在这块更偏实时事件处理，能把低层噪声归一化后给策略层。

我们也做了会话级预算追踪。某次调试可能一口气消耗 500 美元，我可以直接把子 agent 限定到 5 美元，再决定是否继续。

**Matei Zaharia**

这个问题上我花了很多时间，因为我也是 CTO，不想因一个奇怪的命令导致数据泄露或事故上热搜。

同时我也不想每一条 bash 都让人手工确认，这对安全团队和业务效率都不友好。

**Swyx**

安全和 token 成本之间谁更重要？

**Reynold Xin**

看公司类型，不太一样。对大多数企业来说，安全是红线，token 花销在我们看来是工程成本和治理问题。

不过我们会分析 traces，找出模型和场景的异常，持续优化和调度，降低浪费也是长期工作。

文档和 GitHub 样例还是最实用入口，我们会把常见 policy 开箱写明。

## Dream Engine、LTAP 与数据库架构

**Swyx**

你们经常提到 LTAP 与 Dream Engine，我再请你们系统讲一遍。

**Reynold Xin**

数据库世界常见 OLTP 和 OLAP 分离。交易库负责单点更新，分析库负责聚合、报表、机器学习，但现实是大家经常要在两边搬运数据。

CDC 就在这种场景很常见：它读 binlog 做变更同步，但一改 schema、一个链路抖动就会导致数据延迟或损坏。

所以大家问我们：为什么不一开始就只做单库，既能事务又能分析？理论上是 Holy Grail，但工程上很容易互相妥协。

Dream Engine 其实是从这个痛点出发。我们更关心统一存储层，尽量把行格式与列格式的优势按场景转换。

例如 Postgres 写入后我们转成 Parquet 再做分析读取，很多时候速度和成本都更好，且不需要复杂中间管道。

这对 agent 特别有帮助：当 SLA 问题出现时，模型可以直接看到一线数据库上下文，而不只是外部监控指标。

**Matei Zaharia**

这条路线不是一次硬切。我们做的是增量 rollout，先上线端点，再逐步带来新能力。

否则公司很容易陷入‘第二系统综合征’——重构太大、试错太慢。我们不想花五年看不到结果。

另外，我们把数据库工程团队文化做成实验文化：先验证，再扩展。只要能通过真实 traces 验证，就逐步演进。

**Reynold Xin**

你也多次强调模型选型的动态性。不是固定一个算法，而是用 trace 数据在不同 workload 下做高保真选择。

比如 hash、数组、压缩和索引策略都取决于字符串稀疏度、延迟要求、distinct 值等参数。你要根据数据分布选执行路径。

简而言之，就是给查询引擎做‘工厂化’调度，而不是每次都靠手工假设。

**Matei Zaharia**

我们希望未来很多行业数据库（像 TigerBeetle 这类账务系统）也能在同一方向上收敛，很多 2023 年所谓向量数据库也开始变成通用存储的一部分。

当然查询语言不一定统一，Agent 对 SQL 之间切换没那么脆弱，它更关注数据可达性和语义可用性。

**Swyx**

这会改变企业客户的选型思路吗？

**Reynold Xin**

企业和初创公司的差别很大。前者有很多历史系统和合规要求，后者更偏自建。我们要在‘开源生态 + 成熟控制面’之间找平衡。

你很少见到只做一个点对一个客户就成功，很多时候要从小做起，不必在开始时做“全行业完整方案”。

**Matei Zaharia**

我们会反复做一些客户案例：有公司先要入库入湖、加库监控，有公司要我们直接帮他们一起做 eval、合成数据和部署。两类需求都在。

## 与 Snowflake 的开放之争与 AI 方向

**Reynold Xin**

你们和 Snowflake 最大差异之一是：Databricks 一直强调开放格式。

Databricks 从 Parquet 出发，后来接入 Delta、Iceberg 这类生态，能让数据资产容易互通，不必被单一供应商绑定。

**Matei Zaharia**

早期我们都把平台设计为 ML + data；AI 的兴起让模型语境和数据交付发生了变化。我们更愿意在开放数据层上做可插拔的 AI 能力，而不是关在单一模型里。

我记得当初有人认为我们会完全走 proprietary 路线，但我们更看重 long-term 的生态锁定风险。开放格式在企业端更容易被接受。

**Swyx**

你们还提到 open format 的争论文章，甚至 Snowflake 的创始人观点都很争议。

后来事实证明，企业越来越希望数据在标准格式里可治理、可迁移，这是 Databricks 的机会。

**Reynold Xin**

Ali 在这块起了很大作用，他会在很多产品分叉点上推动方向，很多时候我们会通过他来快速聚合反馈。

在 CEO 视角与架构视角之间做取舍非常难，但 Databricks 的优势是能把长期投入持续保持。

**Matei Zaharia**

接下来我想补一段 Mosaic 的问题。很多人以为 Databricks 买了它之后会大规模自研 frontier model，但我们现在更重视“把模型用于具体场景”。

我们发布过 DBRX，也在做 RL fine-tuning 与 AI runtime，但现在更关注的是专用模型和子代理，而不是只盯着单一最强参数量。

文档理解就是典型例子。通用模型看起来像懂，实际上成本高、错误率也高。我们做过文档视觉模型，能把页面结构化成 JSON，成本更低且更稳定。

Genie 的定位也类似“内部虚拟数据科学家”：了解公司数据、库、工具和业务上下文，回答问题并推进分析决策。

我们发现很多专用子代理、advisor model、同构训练管线比单一模型更容易落地，因为数据和 trace 质量高时，训练越快。

**Swyx**

你提到接口层仍然是关键。

**Reynold Xin**

是的，统一接口和 composable agents 是我们后续所有创新的前提。没有它们，模型、工具、子代理无法长期组合。

## 上下文价值与未来应用落地

**Swyx**

你刚才提到 Satya Nadella 说 context is the new oil 的观点。你同意吗？

**Matei Zaharia**

我同意。越能拿到完整、及时的数据，AI 的收益越高。不是为了替代人，而是加速洞察形成。

很多行业都是数据不断产生：电网、汽车传感器、工厂系统。价值在于自动把异常和趋势变成可执行判断。

例如产品报障，不一定要等客户投诉。代理可以发现上传骤降、查询异常等信号，提前介入。

**Reynold Xin**

数据库类的资产规模和历史上下文越丰富，新的引擎也越容易迭代。我们在内部就基于大量 trace 采样训练模型，帮助系统自动选执行路径。

对很多企业来说，AI 价值现在不是先做大模型，而是先把数据放对位置，再把 agent 放在其上。

传统软件很多模块会被 AI 时代重写：不变的是对数据访问和安全控制的要求，变化的是交互层。

**Swyx**

你刚才给出的结论很清楚：只要数据正确，前端能力和代理叠加会非常强。

**Matei Zaharia**

对，数据平台、客户数据平台、安全治理与 AI runtime 要一起看。否则你只能获得一部分能力，难以规模化。
