Databricks 对未来 AI 的押注：Agent Cloud（Matei Zaharia 与 Reynold Xin）

本期节目以 Databricks 推出 Agent Cloud 为主线，讨论数据与代理协同在 AI 应用中的核心地位。Swyx 与 Matei Zaharia 回顾 Databricks 从早期 Data AI Summit 到现在 Omnigents、Databricks Genie、统一的 Agent API 与云沙盒服务的路线，解释数据治理、上下文记忆与工具调用如何连接大模型与企业数据流程。双方也讨论了安全策略、访问控制、成本预算和监控的工程化要求，以及企业采用 AI 系统时常见的审计与可靠性约束。后续节目延伸到 Dream Engine 与数据库方向：OLTP/OLAP 融合、CDC 维护、以及单一数据层下的动态执行能力如何降低运维负担。最终，嘉宾认为 Databricks 的优势不只是模型能力，而在于把基础设施、数据协作和代理工作流打通，形成可扩展、可管理的 AI 企业系统。

开场与 Databricks 的访谈背景

Swyx

今天来聊 Databricks。欢迎 Matei Zaharia。你提到 Data AI Summit 从 50 人小型聚会到现在 10 万多社区成员，增长非常快。

Matei Zaharia

是的。最开始在伯克利算是小型聚会，主要是教大家怎么用 Spark。后来规模翻了很多倍，现场和线上参与者都很热络，能看到这个增长也是挺有意思的。

Swyx

你怎么看 Databricks 当前这位 CEO 的表现？我提到的 Ali（Ali Ghodsi）你也熟悉。

Matei Zaharia

我认为他在公司里很适合这个角色。Ali 在十年前和现在差异很大，后来他几乎把很多领域都看了一遍：财务、销售、产品、工程和公司运营。更重要的是他把严肃的 AI 和数据主题讲得很轻松，公开演讲很强。

他也很能让团队协作起来。Databricks 过去这几年推出了 Omnigents、El Tap、Dream Engine、Genie、Unity AI Gateway 等一系列产品，不少是大家早就期待的一类产品能力。

Swyx

你刚才提到两位都在推动了最有辨识度的两个方向。我们先从 Omnigen 开始吧。

Matei Zaharia

是的。主要动机是，内部开发团队在写代码代理（Coding Agent）和很多定制代理（Custom Agent）之间反复切换时遇到同样问题。大家会自己搭建流程，但缺少统一的协作框架。

我们当时看到一个现象：一个好的代理需要支持会话共享、搜索、历史上下文和协作。只要没有这些，代理就很难真正落地。于是我们开始思考把这些“外层能力”前置到统一平台。

Swyx

这个方向和“操作系统”或者“网络协议”有点像？

Matei Zaharia

对，我也是这么看：数据库和操作系统式的基础层非常像。除了具体 AI 能力，真正要做的，是把不同服务和团队间协作变得可互联。比如一个统一数据表视图可以让供应商实时读取销售、库存数据，减少邮件和表格同步。

Swyx

听起来很像把接口从“手工流程”抽出来。

Matei Zaharia

是的。大家常说有了 vibe coding 就不需要协议、接口、软件工程了吗，但当多方以不同节奏开发时，还是需要稳定协议层来做协调，不然协同成本很高。

Swyx

你之前提到自己被频繁深夜coding的体验，是这条路的一个触发点吗？

Matei Zaharia

对。当时有一周几乎连续加班，担心本地机器和客户端崩掉，开车也要用手机热点接着看任务，很不合理。后来我想到：云端沙盒最好不要“熄火”，让你不必一直守着笔记本。

我和团队整理了‘我希望云开发环境具备什么能力’的清单，也包括像 shell、文件列表、日志和 Markdown 渲染。很多东西都从真实使用痛点倒推回来。

另外，大家还普遍有个问题：一个人搭好的代理工作流，团队里别的成员没法复用。于是我们把 Omnigents 做成了可登录、可安全共享、可多人协作的服务式平台。

Swyx

你提到这块还做成了云端共享模型，既能共享也能保持安全边界。

Matei Zaharia

对。我们的想法是，让代理既可安全隔离，也可跨会话协作。你可以理解为把“模型调用、上下文、权限、会话”都接到同一个平台面向多角色服务。

Agent Cloud 结构与开源策略

Swyx

你给听众展示了整个平台结构。给我概括下核心构成。

Matei Zaharia

核心是 Runner 和 Server 两层，再往上有统一 API，外加可插拔的持久化层和计算层。这个形态更像一套“Agent Cloud”基础设施。

一台机器上跑不同代理，基本都能接入；但真正重要的是有了一个主机服务，任何团队都能复用起点再做定制，不需要重复造轮子。

我们开源的原因之一，就是想形成生态网络。Spark 的经验是，真正有价值的往往是“底层层次可扩展”，不是每家公司都自己写 connector。

就像 Spark 里把分布式引擎变成库并开放生态，Databricks 也希望把代理运行与会话控制这层做开源。企业级更敏感的运营层面仍然由公司把控。

Swyx

开源发布后效果怎么样？

Matei Zaharia

反馈很快。短期内就看到几十个社区贡献。有人加了 Kubernetes 支持，有人做了很多云沙盒。短时间能迭代出一批互补组件。

更重要的是，生态已经从单点替代转向“有一条主线、很多接头部件”。从开发者体验看，大家希望减少重复集成，尽量把不同代理框架统一到共同接口。

Swyx

这听起来像是在替代“现代数据栈”那种拆分思路？

Matei Zaharia

是的。现代数据栈原本把 ingest、transform、warehouse、可视化拆成不同模块和供应商，后来也有了整合趋势。现在 Agent 场景下更明显：用户做一个简单 Agent 不应该拼十来个系统。

所以我们在上层更想做一个“统一 API + 可插拔 harness”。你发消息或文件创建 session，得到统一的流式输出和工具调用。底层可以接 Claude Code、Codex、OpenAI SDK、Phi，不需要你自己维护多套编排。

Swyx

也就是你们做了一个通用接口层，让上层应用不断开。

Matei Zaharia

对。我们不想做成一整套闭环应用栈，而是让更多团队在上面接自己 UI。这样可组合、可扩展，也更容易在内部产品复用。

云沙盒、计算分离与可观测性

Swyx

你前面还提到沙盒很快做出原型。是怎样和数据库团队相关联的？

Matei Zaharia

核心是在 Lakehouse 架构上把数据库语义和云计算分离开。沙盒要长期持久，开发者不希望每次都重装环境；所以 state、library、文件系统都得稳定。

Databricks 在内部就已经支撑了非常高的数据量和虚拟机规模，我们借助内外部实际规模检验设计，很多东西只有在量级到来后才会暴露。

另外从 Neon 那边得到启发，后来证明数据库和数据库外部计算其实都不是非此即彼。我们也在思考“数据库本身应该内置计算能力”以及如何让实例化环境更快恢复。

Swyx

转到安全这块，我记得你提到上下文感知策略。

Matei Zaharia

对。传统权限是“允许/禁止”，但 AI 代理场景更细：同一会话里某一步危险行为发生了以后，风险边界会变化。我们加了 stateful、contextual policy：读到机密文档之后，再决定是否允许发布。

同时我们把低层事件映射为高层语义，再由策略层判断是否拦截、转交确认或自动执行。这个思路也应用在 Pan​ther 之类事件处理组件，目标是既安全又不打断效率。

还有成本控制。会话里能统计消耗，超预算自动提示或中断，就不需要用户手工盯住每条命令。CTO 最大焦虑之一就是‘不是我能再审批每个 bash 细节’。

Swyx

听起来安全和预算谁更重要？

Matei Zaharia

两者都要，但对云服务而言安全往往优先级更高。预算确实重要，尤其超大客户每月上千美元的边际开销会放大，但一旦发生数据泄露成本更高。

Swyx

对开发者来说，最容易上手的是什么？

Matei Zaharia

文档和 GitHub 示例。我们会把常见策略写清楚，用户按需启用。开发者可以定义自定义 policy，不是所有团队要同一套行为规则。

Swyx

你也给创业者一个建议吗？

Matei Zaharia

创业公司最容易被忽略的是“代理使用模式”和“监控”。你可以先把 coding agent 的质量和使用路径做成可观察，再做更有区别的层。把‘通用代理’和‘行业化需求’对齐。

从数据架构到 Dream Engine：单一存储与实时分析

Swyx

再看你们的 Dream Engine。你说的是数据库方向的“单一引擎”。

Matei Zaharia

没错。很多人把数据库世界分成 OLTP 和 OLAP，OLTP 追求事务一致性，OLAP 做聚合与分析。现在大家都是在这两套系统之间搬运数据，成本和复杂度很高。

特别是 CDC（变更数据捕获）虽然常见，却脆弱：schema 变化或管道故障都会导致数据延迟和损坏。过去十年我们也都经历过 3 点被“叫醒”的夜班。

Dream Engine 的一个核心思路是单一存储层。把原本的行格式转成列格式来服务分析时机，提高 pipeline 吞吐和可用性，让分析和交易共享更多上下文。

这样一来，日志和交易数据能更快被用于智能体判断，比如订单流、库存变动、服务事故就能更及时地被解释，不需要额外做复杂抽取。

Swyx

能不能一口气切到新系统？

Matei Zaharia

不现实。我们是渐进发布，先拿一个 endpoint 做验证，再把能力逐步往外扩展。避免企业上来就经历五年重构失败的“第二系统综合征”。

工程上有一支很强的数据库团队，但我们更强调“可反复试验”。很多最关键的点不是一次性立项，而是边做边验证，边验证边收敛到真正可用形态。

比如我们会先看历史查询特征再让系统自己学习。不是靠单一算法，而是通过多种实现、成本模型和运行时特征，动态选择最优路径。

Swyx

这背后是不是在讲“查询引擎不是固定算法，像推荐系统一样调度”？

Matei Zaharia

可以这么理解。不同数据分布、延迟要求、内存预算、字符串特征，都会影响是否用 hash、数组或其他结构。经验规则和数据特征都要被模型化。

所以我们要做的是建立一个‘查询算法工厂’，不是某个固定执行器。它会在可接受的资源约束下把最可能快和稳定的路径选出来。

Swyx

你也在这个方向上持续扩展，比如 TigerBeetle 这类数据库、向量数据库也在变成通用存储。

Matei Zaharia

对。很多过去看似独立的数据库方向，正在向“通用存储+可插拔查询层”靠拢。ELT 在演进里，很多变更是把存储统一了，查询层未必要强行折叠成一个。

所以即便 Query 语法不同，agent 并不是问题。只要数据可达、语义可解释，代理就能切换到适合自己的上下文。人类对工具选择不熟悉，但 Agent 更不需要你先学习多套 SQL。

企业用户与竞争格局

Swyx

你刚才提到 Databricks 与 Snowflake 的差异。

Matei Zaharia

两家公司都起步相似，都走向云、都从存储与计算分离入手。关键差异之一是 Databricks 一直坚持更开放的格式和协议，比如 Parquet、Delta、Iceberg，这对生态扩展很关键。

其次是 AI 导向。ChatGPT 后我们本来就是 data+ML 方向，后来发现 AI 工作负载要求更激进。我们早期并不适合把 AI 做成封闭内核，而是让 AI 功能在开放数据层上可组合。

企业端和新创公司差异很大。企业有更多治理、采购、合规和历史系统依赖，定制难度高；小公司更愿意自己动手，但也没有精力从头做。Databricks 的价值在于在这两端之间提供统一路径。

我们也相信“合作比过度定制更快”。如果用户需求从 1 到 100 个小众场景，先做核心一致性和可扩展能力，反而比一次性把每个场景都内建更可持续。

模型与 Genie：面向定制化代理的下一步

Swyx

最后聊到模型。Databricks 为什么不急着 all-in 自研大模型，而是在 Genie 和定制化上投入？

Matei Zaharia

你看，在模型层面，“更大更贵”不是长期答案。我们不止发布过 DBRX，也清楚自己不是只靠前沿通用模型赢。我们更关注如何让模型真正可用。

第一步是让模型在企业数据场景里稳定工作，比如文档解析。传统模型在 PDF/Word 上容易出错、代价也高。我们做了专用文档视觉模型，成本能降百倍级。

Genie 的定位就是企业内建的一种“虚拟数据科学家”：它知道公司数据、常见 ML 与数据库库、公开信息与上下文，可以协同回答问题和推进工作。

所以我们更看重“模型编排 + 专用子代理 + 优秀的训练闭环”，而不是单一通吃模型。Mosaic 的经验是，如果模型越多、任务越专业，定制越有价值。

Swyx

你也提到 advisor model、强化学习、自动生成数据。

Matei Zaharia

对，RL 的优势在于你可以基于真实 trace 反复训练。越多高质量轨迹，模型越擅长下一步动作选择。合成数据管线也更实用，某些任务下会比人工标注更快迭代。

真正关键的还是接口和统一 API。只有接口标准化，子代理、工具链和模型后端才能互换。接口层不统一，系统就很难形成组合型 Agent。

Swyx

你对 Satya 说的 “context is the new oil” 的理解是什么？

Matei Zaharia

我觉得他说的是：数据越完整、越实时，AI 的增益越快。AI 不是替代一切，不是比人类更聪明，而是让你更快地发现模式。就像电网、传感器、车辆数据一样，价值在于可执行洞察。

Agent 能自动监测产品异常，比如文件上传下降、查询异常，可能比人工更快发现问题并触发响应。这也是我们把客户数据平台和代理结合的基础逻辑。

Swyx

那 Databricks 目前在模型落地上更偏什么路径？

Matei Zaharia

我们提供 RL 微调服务、AI runtime、GPU 集群和训练栈。不同客户分成两类：一类要基础算力和工具链，另一类要跟他们的工作流深度共建，包括 eval、合成数据和部署。

Swyx

回到开头，结论就是“把数据放对位置”才是关键。

Matei Zaharia

对。传统软件正向前端、后端重构，AI 时代会把同样的软件能力重新包装。只要数据在位，代理叠加上去就会出现“魔法”。

这也是我们最近在 Data AI Summit 同步的两个方向：安全侧和营销侧产品。目标是让数据可达、可控、安全、可扩展。

Swyx

你们这期聊得很细，也很难得。最后有什么给听众的话吗？

Matei Zaharia

谢谢。Databricks 这几年一直在做“先做对、再做快”的事。David 说得对，社区在 AI 经济里会越发看重可协作的基础设施。我也希望这些工作能让更多人更快把 AI 用在真实业务里。

Swyx

你也提到 Ben Horowitz 对公司方向的判断。结尾一句的话？

Matei Zaharia

他对长期价值看得很准。Databricks 不只是现在的产品线，而是对未来基础设施竞争力的一种押注。我们会继续把开放、规模和执行力放在第一位。
