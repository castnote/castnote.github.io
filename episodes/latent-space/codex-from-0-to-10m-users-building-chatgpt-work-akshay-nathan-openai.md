## 开场：从 ChatGPT Work 切入

**SPEAKER_02**

我们正在录音室里采访 OpenAI 的 Akshay。欢迎。谢谢。我们也有可靠的联合主持人 Vibu。

你最近上线了 ChatGPT Work。你负责核心产品工程，这个过程走了很长时间。你提到从 Walrus 和 Airtable 那种无代码、低代码起步，我觉得很有意思。

在我看来，ChatGPT Work 有点像‘超级应用里的超级应用’，说得更直白就是‘终极无代码’：你只需要写一段提示词就能开始。

**SPEAKER_01**

这很有意思，我一直觉得职业生涯里很多想法绕着一个循环走：工程师能够通过代码做很多事情。如果能让更多人以更容易的方式获得这些能力，效果会很神奇。

我以前在消费金融方向开始工作。后来在 LLM 之前，我们也尝试过用 AI 做自动化测试，但那时实现得并不优雅。之后我在 Airtable 工作了一段时间，核心想法很像：如果把数据库或数据库背后的基础能力交给更多人，会非常有价值。

当时我还不确定，但现在看来，LM 的出现就像把缺失的一块拼好了。它让代码的魔力可以更广泛落地，而用户不需要理解底层细节。ChatGPT Work 和之前的探索，某种程度上就是这个愿景的体现。

**SPEAKER_01**

有意思的是，最值得关注的有些地方其实没变。我记得刚入职时团队大概 500 人，我担心的是它是不是还保留初创团队的活力。事实证明这种创业氛围和‘任何人都能从想法到上线’的文化反而更强。

让我继续坚持的，是把前沿智能带给更多人的使命，做 AGI 之后再把它普及开来。技术路线不一定是线性的，肯定会有不同产品、不同实验成功失败切换，但愿景和使命并未改变。

**SPEAKER_02**

你负责过 Enterprise。很多人其实没用过 ChatGPT Enterprise。你从企业项目里带走了什么经验？

**SPEAKER_01**

企业里没有通用方案。早期我们接触客户时，大家都兴奋于把 AI 带进公司，组建了很多 AI 部署团队，预算也很大。

一开始问他们‘你们想解决什么’，通常只会说有大量上下文和数据。追问具体场景后，答案却五花八门。这说明同一个模型在不同组织里，问题非常分散。

问题不在于会不会用，而在于不知道从哪儿开始。关键是把产品带到用户所在的工作流里，先理解他们想解决的实际‘use case’，再教他们如何用 AI 获得杠杆。

所以我会把它分成 go-to-market 与产品层面。前者负责触达和落地，后者负责引导体验：当用户面对电脑或手机时，产品本身要明确下一步怎么做、让他们不迷路。

现在回答你问题：采用增长是实打实的，但机会更大。ChatGPT Work 的核心在于把这种潜力从早期开发者圈扩展到更广泛用户。

那我们聊一口气切到 ChatGPT Work。一个月前才正式发布，背后是怎样的决策过程？是不是把多个‘超级应用’能力收口合并了？浏览器也被弃用了吗？

很多同事从“很神秘的工具”变成“我觉得自己像拥有超能力”。这说明 Codex 与 Agent 的能力已经不该只给开发者，用起来要像 ChatGPT 一样低门槛。

我们要做的就是让这些已有的知识传递给更多人，所以最终形成了 ChatGPT Work 的合并与上线：同一套能力，服务更宽的用户。

**SPEAKER_01**

我们更偏‘生产力’，但不是狭义生产力。一个人可能在个人生活里做很多“像工作一样”的事情，Agent 都能帮助。比如有人丢了快递，我们用一张照片就能去周边平台匹配、定位包裹，给出线索。

Codex 是一个很耐久的产品。我们不想让用户卡在某个 tab 或界面里找不到能力。理想是 desktop 的 Codex 能力在 work chat 里同样可用，反过来也成立。

我们做了很多设计权衡：比如是否展示 git 状态、是否默认暴露 agent 的中间思路、sandbox 和安全边界如何设置。用户不应该被要求手动选择体验边界，系统应该做得更智能。

**SPEAKER_01**

底层是共享的 harness。无论是在 chat 还是 work，我们都在同一套核心能力上做针对知识工作优化，比如 plugins、computer use、artifacts。UX 会按场景不同做不同呈现，但本体能力方向一致。

你可以用一个查询在两个模式里试一遍，比如做退休计算器或表格。Codex 会偏向仓库工作流和 diff 展示；work 侧更像一站式执行，而非直接暴露底层文件编辑。

**SPEAKER_02**

你们的生产力团队除了产品化外，还有哪些分支？能不能再讲一遍现在的组织分工？

**SPEAKER_01**

除了生产力之外，我们还有核心 ChatGPT 团队、企业、基础设施、API 等。ChatGPT 不只是生产力，还承载搜索、写作、学习、图片等非常多的日常需求。

你刚刚展示了 work 和 codex 两种模式切换，我这边也试了 5.6 的任务，放在后台跑了很久。你可以再给我讲讲两者的具体差别吗？

**SPEAKER_01**

最大的差别之一是 context。Codex 假设你在 git repo、会处理 diffs 和文件编辑；而 work 更像任务代理和知识工作入口，不一定要你理解所有开发细节。

也有人会问为什么不完全分离为两个独立 app。答案是因为工作方式本身在持续变化，我们不希望给用户画死界线。先统一底层原语，比如 plugins，等成熟后再让体验自然扩展，而不是人为封锁。

你可以把它理解为一个不断‘发散再收敛’的过程。Chat 主要优化延迟和对话体验，Codex 证明了无限环境下的能力；而 Work 需要平衡这两者，把同一个模型能力带到知识工作场景。

多数人先用默认模型即可，它对绝大多数场景已经很好。先别急着手动调参，先在真实任务里验证收益。如果在效率或结果质量上真的不够，再换配置。我们也在持续简化高级用户的切换成本。

这要看个体偏好和任务类型。互动本身有协作习惯差异。复杂、并行且难以提前定义的任务，可能更适合 Ultra 或多智能体；结构化、可验证推进的长期任务，也可以用 goal。大多数场景建议先默认，再决定是否加速或升级。

**SPEAKER_00**

我个人也很频繁地给它开子代理，尤其是深度研究时。理论上可以配置更便宜或更快的模型来做子任务，省时也省成本。

**SPEAKER_01**

对，方向没错。但我们不想让用户被‘太多开关’打断，所以尽量把参数简化为直观可理解的操作。你可以在对话里说出你的偏好，系统通常会帮你选路由。

你看到的滑杆实际上把速度/成本与质量/深度这两个维度投影到一个控制上。默认通常是一个平衡点；如果你觉得模型跑太快或太慢，再往另一端微调即可。

不过这背后也有默认值策略。比如很多人会一直用效率模式，或者只选某个模型，但默认并不是一成不变；我们希望它可以覆盖大多数场景，高手用到再自定义。

**SPEAKER_01**

我们想平衡两个目标：一是让用户知道工具的能力边界，二是避免被信息轰炸。展示太多细节会认知负担大，但完全不展示又会让人不知道能做什么。我们目前采用“够用而不拥挤”的策略。

那关于合作体验呢？同一份 artifact 在团队里共享是否有多用户方案？

**SPEAKER_01**

目前已经可以共享，协作方向正在持续迭代。更常见的场景是团队里有人把经验通过私聊式方式传来传去，我们还在把这种协作路径做成一等公民。

在一个团队里，一个人做月度报告时，不必受限于某一个应用按钮结构，只要在同一页面就能持续演化，任何人都能补齐缺失字段。对于“更高带宽、少约束”的知识协作，这是很重要的。

我们希望 artifact 既支持展示细节，也能在不同用户能力层级下自动变得可用。对高级用户，更多信息有帮助；对第一次尝试者，默认视图要更简洁。

我更看重的是从“开发者”向“知识工作者”再向“任何人”的扩展。开发者是最早 adopter，已经验证了产品；下一阶段是所有工作者都能用这些原语提高生产力。

## 模型能力与工作习惯：从自动化到可管理的流程

**SPEAKER_00**

给重度用户有什么建议？有人每天全量使用，有人只偶尔触发一次，大家之间差距大。

**SPEAKER_01**

第一条建议是先把想象力放大。技术进步很快，三个月前做不到的事今天可能已经很好地可用。你要持续更新自己对‘可做什么’的认知。

第二条是输入越完整越好。你在本地电脑里的上下文、历史工作、文件、artifact 形成资产库，模型会在这些基础上给出更有质量的建议。

**SPEAKER_02**

尤其是 review 场景，经常有人担心版权与伦理。你会把 AI 用在哪个边界？

**SPEAKER_01**

我不会建议把完整的评审文本完全由 AI 直接发出去。更好的用法是用于搜集上下文、整理信息、做 agentic search。人还是要保留最后审核，判断语气、价值和合适程度。

像 Slack 里消息量很大，模型会偶尔遗漏也会漏检关键内容，但人同样会遗漏。关键是把这种能力当成“发现遗漏、补充线索”的助手，而不是完全替代。

**SPEAKER_00**

我们内部也有类似做法，比如给项目配 secret 的自定义文件索引。经常会少点费工，但一旦模型找到历史已有内容，省下不少时间。

**SPEAKER_01**

我还见过团队成员做过自动化总结：把 Slack、文档、讨论的脉络定期抽取，汇总到一个共享频道。虽然有时它会‘讲得很有趣’地组织内容，但能暴露很多隐性信息，这是以前难以系统维护的。

**SPEAKER_02**

今天这个发布很成功，据说 1000 万用户里程碑也接近了。对你来说，100 万到 1000 万的变化是什么感受？

**SPEAKER_01**

这是一个里程碑，也意味着我们把内部验证和长期愿景带到了更广泛用户。核心目标仍然是把“ChatGPT 的魔力”给到更多人，不只是让少量高意愿用户体验到。

我们也没有一夜之间强推所有人到 Work，因为它是付费功能，目前还要通过教育、反馈、体验优化逐步推进。未来目标是让几乎所有 ChatGPT 用户在自己工作和生活中都能自然触达这条线。

Codex 仍然会保留品牌和核心价值，我们会持续把软件开发体验做好。工作与对话并不是互斥关系，而是同一条产品路径上的不同入口。

**SPEAKER_02**

你刚才也提到过 OpenClaw 式的个人代理，我想问会不会逐步替代？

**SPEAKER_01**

我自己有过用 OpenClaw 管理家庭任务的经验，比如日程、健康、工作清单。后来发现 ChatGPT Work 的持久化环境和文件系统，其实能做更多相似用例，尤其是个人和工作交叉场景。

但我不认为它会取代所有开源方案。更多是让这些灵感被更广泛的人群复用。我们会在可持续的前提下，把这种“个人代理”能力嵌入更大分发渠道。

**SPEAKER_00**

那我可以在 ChatGPT Work 里处理个人财务、健康类需求吗？比如预算、退休计划、健康信息整合。

**SPEAKER_01**

目前还不能托管你真实的现金和资产账户，但财务规划和预算类应用逻辑已经逐步覆盖。把所有信息接入后，你在一个入口就能问“我的退休/预算/健康情况”并得到可执行建议。

传统金融 app 需要很多过滤器和界面来引导，Work 的价值是只要把数据连接上，你更像是在对一个统一的知识仓库提问，而不是在多个应用里反复搜索。

## 记忆系统与可扩展协作

**SPEAKER_02**

回到记忆和安全性。最近大家都在讨论 memory，像“Chad Gypsy 的新 memory 不够好”之类的反馈很多。你怎么看？

**SPEAKER_01**

这确实是大问题。Samir 和研究团队做了大量改进，尤其在持续记忆方面。大家最认可的是，模型能更稳定地记住你是谁、你在做什么，这会显著改变体验。

ChatGPT Work 天然继承了 ChatGPT 的记忆系统，默认会把会话上下文与长期记忆关联。关键不是只“记得”得多，而是能在对的时机、对的上下文里“想起来”。

另一个方向是 Chronicle，这个功能会从电脑使用行为中学习，作为额外输入源。它是实验性功能，默认并非全量开启，但我建议大家试用，尤其适合长期检索和自动化洞察。

**SPEAKER_00**

从 Chat 走向 Work 的记忆机制，和项目协作里多个会话线程相比，有什么不同？

**SPEAKER_01**

你可能会认为 chat 是一次性对话、work 更像持续项目。我理解这个差异，但本质是同一套能力可以覆盖不同粒度。Chat 有大量短会话，Work 更偏长期、持续的任务序列。

我个人在 ChatGPT 上也看到这些‘碎片化输入’会慢慢沉淀成稳定画像。所以问题在于如何把这种深度持续记忆拿进 Work，同时避免误召回和噪音。

**SPEAKER_02**

有时我们会问它能不能找到我们没想到的东西，它确实会有 false positive 或 miss。这个权衡你怎么看？

**SPEAKER_01**

这个问题我不负责底层记忆模块，但可以肯定是两方面：一是记对了哪些事实，二是以合适情境提醒这些事实。检索准确率和干预策略都是开放问题，需要持续迭代。

## 效率衡量与组织管理

**SPEAKER_00**
