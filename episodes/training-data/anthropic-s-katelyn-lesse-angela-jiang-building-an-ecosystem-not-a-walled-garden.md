## 开场：Anthropic Platform 的定位

**Angela Jiang**

在抽象层次上，知识层、执行层之外最上面还会有一个协调层。我觉得我们正在尝试把这个层次做得像 meta harness（元编排层）。底层 harness 负责执行，但 token 在很多场景下并不等价，某个 token 可以是建议型决策，另一个可以是实际执行。我们要把这些有组织的策略串起来放在上层，但最终仍必须回到执行层，确保任务能落地。

欢迎两位加入。非常高兴你们今天来访。你们负责 Anthropic 的 Platform，我认为这是世界上最重要（甚至最重要）的开发者平台之一。想先听你们给我们一个背景：Anthropic Platform 到底是什么？你们在公司里的定位是什么？

Platform 既包括面向外部开发者的 API，也包括内部开发者和产品团队用到的平台能力。对外是开发者平台，人们在上面接入 Claude 打造应用和系统；对内我们也在跑自己的产品基础设施，是内部产品共同构建的那一层。

**Sonya Huang**

你们团队的 north star 是什么？

**Angela Jiang**

好问题。因为我们同时做内部与外部两套业务，所以实际上有两个 north star。听起来像矛盾，但确实是两套动力系统。

**Sonya Huang**

（笑）一个像是不同星系。

**Angela Jiang**

对，外部可以类比成两个独立轨道。对内我们更强调让团队有足够杠杆去快速推出 AGI-pilled 的产品，让他们在可靠的平台上更快迭代。

对外的目标更偏宽：给每个 builder 够用的工具，让他们能用 Claude 做想做的事情。我们要把平台尽量贴近具体业务，所以会和超大规模基础设施提供方合作，比如 AWS、Google，尽量在这些生态里更容易接入。

我们做的其实是大量 primitives。目标是让开发者表达自己的产品愿景：即便是自定义软件，也越来越可行。我们会把能力分层输出——有时是 primitives 和 API，有时是更高层抽象，有时是标准，比如 skills、MCP。我们不是只做一个产品，而是尽量把可复用能力开放给生态。

总的来说对外的方向是‘帮助你构建’，对内则更偏重可靠性和速度。

**Lauren Reeder**

那你们如何决定什么东西能放进平台，什么又需要外部化？哪些产品应该对外开放？

**Angela Jiang**

核心原则是保持一致性。很多平台会把内外业务分开做，但我们不想。内部和外部 builder 都是 user，只是需求不同。我们尽量给所有人同一组原语。

更深层原因是模型能力增长太快，形态会不断变化。两年前大家都在“聊天”，现在大家在讨论“agent”，下一波又会变化。能预先定义一种长期不变的形态很难，因此我们更重视给人足够的可组合能力，让形态自己从市场里演化出来。

**Katelyn Lesse**

团队里确实会反复做实验，比如把同一组 primitives 重新打包到更高抽象层。我们常常先在内部做一次，然后再给外部用户 early access。这样能从两个群体拿到反馈，把结果再回流到平台，不会被内部需求绑架，也不会只听外部的某一种声音。

**Sonya Huang**

你刚才提到更高层抽象。最底层是 Claude、Opus 等接入能力。那你们怎么定义上面的层级栈？

**Katelyn Lesse**

我一年前加入时，Anthropic 平台主要是 Messages API，基础上有 SDK、文档、控制台等开发者工具，整体还是偏无状态 API。随着模型可以跑更长上下文，客户反复遇到同类问题，于是我们开始把基础原语拼起来，补上内部同样需要的基础设施。

最典型的是执行层问题：如何按需创建和销毁 sandbox（含治理和安全）、如何在会话中存储与恢复上下文。这个层级对客户特别有价值，因为大家不想重复造底层。

第二个大块是 harness（编排）工程。包括 prompt caching、context window 管理、成本控制。我们就是把这些以前重复且繁琐的部分更多内置，从而让你在构建系统时把精力放在业务本身；如果你愿意，也可以把这些工作继续外包给我们。

**Sonya Huang**

用户通常是更偏爱原生积木，还是偏爱托管 agent，一键式管理？

**Angela Jiang**

取决于用户画像。AI-native 的创业团队通常更喜欢 primitives，因为他们愿意在底层打磨；企业型客户或业务型团队更看重拿到可直接落地的高阶方案。

## 三层抽象：知识、执行与协调

**Angela Jiang**

我给你一个简化框架：底层是知识层。这里包括对模型的认知、工具使用方式、什么时候该怎么调用。比如 Messages API 的参数设计、tool call 行为、以及我们对 skills、memory 的标准化——它们都属于知识层。

在执行层，重点是‘会做事’。你不只要回答问题，还要输出、改文件、协同多系统。Claude Managed Agents 就属于这类：更低层是 harness 加上托管基础设施。

**Katelyn Lesse**

今天这个形态我们只是起点。前面是知识层，接着执行层，而在上面会形成协调层。协调层在研究的是 token 的角色分工，比如某些 token 做规划、某些 token 执行、某些 token 负责反思，最终再落回执行端。

从路线图看，平台会从知识层逐步向执行层、再向协调层迁移。也就是越来越多地提供可组合的策略，而不是只提供单个能力。

**Sonya Huang**

这个分层框架很清晰。

## 从平台到生态：开放标准与协作

**Lauren Reeder**

这怎么落到更广泛生态？你们如何帮助开发者把这些能力组合成产品，并让每块价值发挥出来？

**Angela Jiang**

这是我们非常在意的方向。产业正在快速变化，很多组件会出现又消失。我们希望在底层先放出足够多的 primitives，让大家有材料去“组合和创造”。

我们一方面做第一方产品，另一方面也做开放连接。比如 connectors（基于 MCP）是为了更原生的接入。我们希望任何公司都能搭在这套能力上：自己做产品，自己开发 agent，甚至让它们和其他 agent 互通。

标准化不止是互操作性，也包括安全。行业里的公司其实都不想自己的服务被滥用、被攻击、被欺诈。我们更看重跨公司协作，共同定义接口和安全规范，让关键基础设施更可靠。

我常说：这项技术像电力。没有电你只能点蜡烛，能做的很有限；有了电，每个人都能接入，前提是有标准和插口。没人能靠单点能力把这一切自己做完，生态协作是必须的。

**Sonya Huang**

你如何看 open ecosystem 与 walled garden 的关系？哪些能力要你们自己持有，哪些你们乐于通过生态集成？

**Katelyn Lesse**

从 Angela 的分层模型看，像执行层的许多功能并不要求一定在我们基础设施上运行。只要接口一致，我们可以让你选择自己托管的 sandbox，或搭配 Modal、Vercel、Cloudflare、Amazon micro VM 等。我们已做了 self-hosted sandboxes 和 MCP tunnels，让内部网络里的服务器也能被安全调用。

真正重要的是架构是否稳健、可扩展，是否按我们定义的接口组合得好。这些都不必绑死在单一供应链。

**Angela Jiang**

有些形态不是长期不变的，比如 Claude Design。我们会不断试不同 form factor。不是因为下一项业务规模最大，而是因为某个问题长期没被解决，模型能力提升后也许能用全新方式处理。

**Lauren Reeder**

那你举个例子。

**Angela Jiang**

Claude Design 是一个例子。它鼓励更多把思路交给 Claude，而不是先手工搭建模板；你可以让它生成代码、生成设计方案，再由你微调。它也提醒我们，代码在 AI 场景下不只是开发工具，而是一种更通用的生产方式。

我们内部会大量实验。这些形态有时只会存在很短时间，但能检验方向。另一方面也会看 TAM（市场规模）和业务需求，编码、制造等高互动迭代场景通常更适合 agentic workflows。

**Katelyn Lesse**

在金融、法律这类高风险场景，大家做法也不同。你可以直接基于 Messages API 构建，也可以直接用 Claude Managed Agents，或直接做 plugin、connector。最近我们上线了 Claude for Financial Services，配套 skill 套件和教程，帮助用户在自己产品里快速起步。

Claude Tag 也是一个打包案例。市面上有人做过 Slack-based agent platform，目标是把全部上下文接入，变成随时可用的工作同伴。Tag 更像这个方向的一个实现。

**Sonya Huang**

很多人只把 Tag 当 Slack 机器人，你觉得这种理解有偏差吗？它的核心优势到底是什么？

**Angela Jiang**

界面只是入口。真正关键在于 context engineering 和架构设计。Tag 在使用上虽然是 @Claude，但后台需要把上下文、权限、记忆和执行策略都接好，才能像同事一样先验理解需求并主动完成任务。

对非技术用户尤其重要：用户可以只是在频道里告诉 Claude 你想完成什么，而不是在多个系统间来回切换。我们负责做掉复杂性，让协作更像“在组织里有一个懂业务的同伴”，而不是一堆工具拼接。

Andrej Karpathy 曾说过这是 org-level harness 的方向，这点我非常同意。真正复杂的内容往往在水面之下：上下文组织、规范化、执行策略。界面可以变化，最终都要服务于长期可用的 agent。

**Sonya Huang**

你们讨论过 context 与 harness 很多次，我猜这部分也包括很多底层经验。你能给开发者给几点建议吗？

**Katelyn Lesse**

首先把 prompt caching 用好，成本会明显降。其次让上下文窗口尽量干净，不需要的内容及时清理。工具链也要自动化，不要把垃圾全塞进上下文。evals（评测）也很关键，没有评测就很难验证效果。

更上层是 strategies（策略）或 meta-harness。传统 harness 可以在“用户-模型-工具”循环里工作，但我们更看重把 token 分层使用：让 token 有些用于执行，有些用于反思并写入 memory，有些用于更强模型的指导，有些用于 grader 打分反馈。

这样做的收益通常比只调底层缓存或 context window 清理更明显。我们现在也在围绕“token jobs”这件事做很多优化。

**Angela Jiang**

你看模型能力的发展让它更可控了。两年前需要很多 scaffold（固定路径）把模型推向目标，现在模型能自己“懂怎么走”，更像是在 prompt 里给方向即可。

所以 harness 越来越少做低级 steering，更多要能让 agent 在目标完成后继续推进。不是停在 B 点，而是能继续到 C、F、Z，然后再回到你这里。这个需要更高层的策略层能力。

**Sonya Huang**

你们认为 task-specific 或 vertical-specific harness 有意义吗？

**Angela Jiang**

我认为有意义。没有万能的 single harness。通用能力像 coding 非常广，但某些行业需要定制化。尤其是错误处理、验证流程，像法律和金融这类高风险场景，最后一公里逻辑会决定成败。

其他场景则可以更多靠 general model 能力。我们看重的不只是上下文长度，而是 token 与数据的匹配：数据越精准，收益越好。

**Katelyn Lesse**

很多人用 harness 一词含义不同：有的人只理解为 user-model-tool 的闭环，有的人把工具都算进去。我的看法是，真正值得自己投入的通常是更高层：比如让 token 去分配、复用、评估，而不是只在底层做 prompt 缓存或清理历史上下文。

理想状态是你只告诉 agent 输出目标和预算，它就执行。不同任务可以在不同层级由你选择控制程度。

**Lauren Reeder**

平台团队最有价值的一点是能看到最前沿用户。你们最近从用户那里学到什么？

**Angela Jiang**

创新不只是新产品界面，而是 context 处理。很多客户很擅长把分散在多个系统里的上下文先聚合，再按权限喂给 agent。尤其是 AI-native 公司，他们在这方面成长最快。

还有很多传统软件环境尤其痛苦，比如部分医疗系统连 API 都没有。用户正在尝试用 computer use 这类能力，把这些旧系统也接入自动化，这说明上下文和连接能力未来非常重要。

**Katelyn Lesse**

我们还看到一个有趣案例：客户有一套基于 Claude Managed Agents 的 agent，又有另一套在其他模型和平台上。把 MCP 服务器放在上层后，不同模型的 agent 可以互相调用工具，协同明显更强。

最近一个趋势是使用场景更外延：不仅是 coding，制造行业也在把 AI 引进工作流。我们看到需求在变，代表可探索空间很大。

## 成本、复杂度与路线图

**Sonya Huang**

看来我们从“token maxing”进入了“token rationalization”阶段。你怎么看？平台端如何支持？

**Angela Jiang**

你这个提法很贴切。模型能力上限会提升，下一步自然落到成本和速度。我们最常强调的是别直接禁止 AI 用量。很多公司一开始会出现 shadow IT，员工自己找渠道用。更好的做法是帮客户做策略路由，让系统自己按任务复杂度分流。

简单说就是：复杂任务交给更强模型，低复杂任务交给更便宜模型。再配合一些路由规则，你可以在成本和效果之间平衡。

**Sonya Huang**

那你们会推出 RAG 吗？

**Angela Jiang**

在 Claude 的语境下，这是有意义的，我们正在设计可重组策略。我们更倾向于把大量 primitive 拆开重组，而不是一次性锁死架构。对模型路由这件事我们也会继续偏向以 Claude 为主，不太想主动建议随意切到其他模型。

**Katelyn Lesse**

我们还认为 harness 和 agentic layer 应该和 model family 一起优化。以前大家以为可以在一个 harness 上随意换模型，但趋势是越往上越看重模型家族内的策略匹配。

我在 Stripe 的经历提醒我，工程管理同样重要：像控制后台任务账单一样，你要有护栏，避免无意消耗。对 AI 也是如此，不能只‘开个上限’然后算完。要让模型在预算内仍有创造性，靠的是更好的策略设计。

**Lauren Reeder**

接下来几个月你们最想做什么？有什么方向能先透露一下？

**Angela Jiang**

我们反复提到的重点是策略编排。很多开发者现在 build bug-hunting agent 后通常只会调模型大小或延长时间，其实还可以通过 best-of-N 等方法提高命中率。问题是它很难工程化。我们正在把这件难事变简单。

**Lauren Reeder**

听起来像一年前的 agent swarms 讨论。

**Katelyn Lesse**

是，已经很久了。

**Lauren Reeder**

好像已经一年了。

**Angela Jiang**

没错，这正是策略的一种：把 token 看作不同职位，不是同质化资源。我们会继续探索更多岗位式 token 分工，这样组合数会从十几个变成十万种。

**Katelyn Lesse**

我们要继续做的是在‘每美元产出最大智力’上做爬坡优化，同时兼顾企业场景里的安全合规。平台要可插拔，要能支持不同团队的人群，不论是周末开发者还是企业安全负责人。

对企业来说，体验必须好：你要知道在哪里填上 memory、连接哪个组件、如何控制策略，否则技术再强也很难真正部署。对个人开发者来说，我们也希望保持开放和可 hack，降低起步门槛。
