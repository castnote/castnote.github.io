Factory 创始人 Matan Grinberg：软件将开始‘自行构建’的软件工厂到来

本期嘉宾 Matan Grinberg 回顾了 Factory 从 2023 年起步到 2025 年后转向成熟的过程，核心在于从追求“完全自主智能体”切换到贴合企业开发者工作流的 Droid CLI，并通过模型中立和可替换架构建立客户信任。对话中他强调了产品价值不在于单点模型，而在于模块化、测试验证和组织层面治理，解释了为什么要退潮性地调整路线、提前退款、保留可迁移资产，以及通过 Router 在任务级动态分配模型。节目还讨论了从 token 消耗到结果导向计费的行业演进、开放模型与闭源模型的博弈、以及公司级能力重塑：从人治、拍脑袋转向可量化的软件工厂方法，以便把工程资源更多放在高杠杆问题上。Matan 预计未来更多使用场景会从同步交互走向异步智能体执行。

正式对话

Pat Grady

欢迎回来。我们今天在工作室和 Factory 的 Matan 聊天，这也是他第二次来 Training Data。

Matan Grinberg

谢谢邀请。

Pat Grady

在 Training Data 历史里，能来到这里二次参加的人很少。

Matan Grinberg

是啊。

Pat Grady

Matan 是 Factory 的联合创始人兼 CEO，做的是面向软件开发的 droids，也就是可以自主工作的智能体。

Matan Grinberg

没错。

Pat Grady

我们直接切入。你们在软件开发市场看起来像一匹黑马。Claude Code、Cognition 等已经起步很快，但你们追得很快。你能谈谈竞争格局，以及 Factory 的独特之处吗？

Matan Grinberg

我们已经创业三年半了。2023 年 4 月，世界尤其是企业市场几乎还没准备好 GitHub Copilot，更别说完全自主的智能体。前两年对我来说像一段沙漠期：我们专注于 fully autonomous agents（完全自主智能体），但工程师和企业采购都没准备好。

所以后来我们把这两年当作磨炼：如何为企业开发者真正可用。等到市场成熟后，我们才更容易被理解。如今我们正在更大规模成长，像 Anthropic、OpenAI 这类分发力很强的玩家在推 Claude Code、Codex。企业真正重视的是：不想把关键能力押到单一厂商身上，不想把命运交给单点。

企业都从云上学到了教训：一开始签约很容易，三五年后续约却可能被抬价十倍。AWS、Azure 这类经历大家都记得很清楚。我们不能让关键流程依赖单一点，也不能让模型厂商替我们定义所有选型。

另外，开发者其实更在乎模块化。新模型出现得更快、更便宜、更强时，他们希望能无缝替换。Factory 能做的就是把“可替换”做得更轻松。

Pat Grady

我总会担心企业会担心从 Codex、Claude Code 切到你们是否只是换了一个锁定点。你怎么回应？

Matan Grinberg

这是关键问题。我们的设计目标是：即便未来你决定不用 Factory，现有自动化和技能注册表也能留在你的代码库，不是藏在我们那边的‘组织秘密知识’。你可以把我们写的成果接手继续用，这样关系就不是把数据与模型控制权锁死。

客户最关心的其实是体验和可控性。我们帮助你在不同模型间做成本最优路由，但不把收益拿走，优化结果仍然属于客户。信任就是在这层。

Pat Grady

前几个月我们聊到你很早就看到了市场方向，但你说过‘早了两三年等于错了两三年’，可以展开讲讲吗？

Matan Grinberg

可以。我当时既没工作经验也没管理经验，就从博士阶段转了身。为了这条路，我说服了 20 位我见过最聪明的人离开原单位加入 Factory，他们中不少有家庭、有孩子。那两年几乎都在教育市场：这个方向难，不是技术不行，而是行为上没准备好。

我们去做开发者 NPS 问卷时体验很明显，开发者会用脚投票：喜欢就继续，不喜欢就非常明确。产品早期确实没有打动他们，这不是主观猜测。

那段时间我还在学企业销售，物理博士背景并没直接帮上忙。现实很残酷：你可以擅长签单，也能拿到收入，但如果开发者不喜欢产品，最终就会崩塌。我们曾经接近 200 万美元收入后意识到产品不够好，于是决定把这部分客户退款。

Pat Grady

当时为什么敢做这个决定？

Matan Grinberg

因为我们卖的是“正确愿景”，却没法证明交付的产品符合。我们坚持的原则之一是客户痴迷度。若产品无法让客户真正满意，就不该硬撑。

这也让我更明确理解了‘顾客至上’和‘输入指标’的区别：不是你宣讲了多少次以客户为中心，而是是否交付到客户以为足以长期依赖的质量。就像篮球不是要求球员先出汗，而是先得分。

我们当时也在团队内提前感到节奏对了，技能、流程和工具都在慢慢“agent-native”。但我们确实走得太快，领先于客户采用速度，结果只好先暂停、等待，才不失去信任。我们向客户说明三个月后再交付成熟版本。

Pat Grady

客户反馈是如何？

Matan Grinberg

有的很支持，也有疑惑。企业通常预算一旦花掉，很难追回，所以有些客户甚至不知道能否申请退款。更难的不是客户，而是向相信你的投资人讲清楚：这份看似增长的收入马上会归零。

后来全员会中也很痛苦，大家都在问‘会不会要倒闭？’。能撑住团队的原因是我们一开始就只招了使命感极强的人，大家知道命运在自己手里，只有透明和坦诚才是唯一可行。

Pat Grady

你是怎么把团队带过来的？

Matan Grinberg

坦诚把情况摆在桌面，说“现在不行、必须重来”。这并不优雅，但这正是建立韧性的时刻。我们也引用了一些耐力运动的例子，像赛艇、体育赛前冲刺那种压力：越难的时候，大家越知道自己是否能一起站住。

公司最初估值 500 万美元。很多后来“天降独角兽”的公司没有经历‘不是独角兽’的阶段，我们却经历了。反而正因如此，后来熬过来后更有韧性，也更懂得未来会再有坏时刻。

Sonya Huang

我很喜欢这个点。那接下来发生了什么？你前面说模型变好不是唯一最重要的变化，但从我视角看它很关键。能细说你的意思吗？

Matan Grinberg

最大变化是交互模式，而不是单纯模型。我们最初直接做 fully autonomous agents，但那要求开发者一次性改变工作习惯，过于激进。到 2025 年 9 月 26 日，我们发布 Droid CLI，更贴近开发者实际的工作流，世界也更习惯 autocomplete 与 chat-assisted coding 了。

开发者真正转变并非只因模型更强，还因为他们逐步接受这种协作方式。企业内的工作流程有三十年惯性，“AI 工具能不能做我的手艺”是天然抗拒点。关键是降低门槛，先教会怎么配合这些工具。

这改变是模型进步与心智模型更新共同作用：模型更强，护栏需求更少；同时开发者愿意试错、愿意尝试新方式。Andrej Karpathy 后来公开支持这类研究，也确实加速了许多人对智能体协作的接受。

Sonya Huang

刚才你提到“Frontier performance soda”这一说法，你的意思是什么？

Matan Grinberg

基准测试有很短的半衰期。一个好 benchmark 往往三到六个月就被模型学到。我们发布时比较关键的是 Terminal-Bench：它测试的不只是改单文件，而是终端环境下执行、编排、运行等综合开发任务，所以更接近真实工程。

Sonya Huang

大家常说自己的 harness 更好，是否就一定要自己做模型才能领先？Benchmark 被追平后，你们如何持续保持前沿？

Matan Grinberg

关键不在“拥有模型”，而在 harness 设计。缓存率、长会话压缩（compaction）后保留关键 needle-in-the-haystack 信息、工具编排能力、环境验证闭环，都会放大性能差异。

Sonya Huang

所以你认为把模型和 harness 一起训练的直觉不一定成立？

Matan Grinberg

对，类比历史会更好：你以为给专属模型喂个人数据会最优，后来发现更好的反而是大规模数据。模型和 harness 也是如此。接入更多模型能避免 harness 对某个模型过拟合，你会学到更多差异，然后反向提升。

最初每个新 Opus 或 GPT5 模型在 Terminal-Bench 上先在 Droid 表现更好，这让我们也困扰，因为不想让客户被某个 harness 锁死。真正可扩展的方式是多模型 harness，而不是押注单一家。

Pat Grady

你能举个更直观的例子吗？

Matan Grinberg

比如同一个任务，Opus 更像“有主见的同事”：会挑选替代方案，甚至自己删掉五个不必要子任务；GPT5.6 更像执行导向，像清单化地把所有步骤做完。我们需要给不同风格提供稳定体验，不让用户在模型间切换时丢任务上下文。

Sonya Huang

你举的这类例子很关键，因为它直接影响可用性。

Matan Grinberg

对用户而言，切换模型前后最要紧的是体验一致。比如代办清单是迁移、修复、调试等长流程的核心，不能一会儿有清单一会儿没有。否则在压缩阶段会丢关键状态，后续就不知道第七步在哪里。

Token 与路由机制

Sonya Huang

我们把话题切到 token maxing。现在行业似乎从‘怎么用更多 token’转向‘如何理性分配成本’，Factory 怎么看？

Matan Grinberg

我先给个版本图景：第一阶段没几个人信 AI，第二阶段全行业都信，第三阶段是 CEO、CTO 被要求做 AI 战略，第四阶段把 AI 写进绩效考核，第五阶段就是 token maxing，大家问任何问题都丢给模型。

这导致一些企业每月花上十万甚至更高去问天气、基础 Python 这类低价值问题。我们不是说这种试水不必要，但后来必须过渡到更成熟的使用策略。Factory 的关键就是 Router，让不同任务按场景分配模型。

对每个组织来说，token 的价值不是均一的。不是所有人都需要同样额度，尤其在大型银行里，给每个人同一 token 上限没有意义。业务要根据任务类型、风险、模型表现做动态路由。

例如前线业务人员可能只需 Gemini Flash 处理低风险任务；维护 COBOL 的团队则可能需要专门微调模型。还有更关键的场景，需要高可靠性时可把“生成-测试-复核”按不同模型分工。

Sonya Huang

那开放模型现在接近什么水平？哪款值得关注？

Matan Grinberg

目前 GLM 5.2 的表现很强，内部已经对部分工程师开放 token 上限，一半的 token 在测试中都使用开放模型。它们通常更快更便宜，许多场景下接近上一代闭源前沿模型表现。

Sonya Huang

你这边是把它看成“前沿减一层模型”吗？

Matan Grinberg

可以这么理解。很多人把公开模型直接拿最新模型比较会误判。开放模型通常比它对应的前沿版本落后一个版本，成本和效率比上去后反而很有吸引力。对企业来说，这意味着更多问题可用更低成本解决。

类比起来像请私教：代数辅导不一定要请爱因斯坦。多数任务能用“足够聪明但便宜”的模型解决，真正稀缺的是复杂决策时那一小部分高价值 token。

Pat Grady

你能分享一下客户端模型分布变化吗？

Matan Grinberg

今年初企业几乎没有显著路由策略，更多是有无。到第一季度才有个位数% 的开放模型 token，占比逐步上升到双位数。注意这是 token 占比，不直接等于成本占比，因为开放模型更便宜。

Sonya Huang

你预期未来趋势？

Matan Grinberg

我预期开放模型份额会继续增大，但不会是 100%。核心决策节点仍需要 frontier intelligence。未来企业会把高杠杆时刻留给前沿模型，把低杠杆的重复劳动更广泛地 offload。

工程师写文档是典型低杠杆任务。即便高水平工程师花大量时间写文档，也是可替代的。自动化以后，他们能把时间投到系统设计、复杂问题判断上。

Sonya Huang

这会推着商业模式变化。你们怎么看定价？

Matan Grinberg

短期看 usage-based（按用量计费）是更现实。Seat-based 对我们意义不大。我们认为未来更可能走 outcome-based（按结果计费），不过企业还没完全准备，可能在 2030 年代才普及。

Pat Grady

结果导向计费如何定义？

Matan Grinberg

现在是“用多少付多少”，未来则更像一个小型 marketplace。任务提供者出需求，模型厂商报价格与可交付水平，用户给出验证标准并验收。买卖双方都按验证回传做决策，像一个更细颗粒的任务竞价机制。

挑战在于任务细分：要定义任务、验证标准、失败容忍度。工具越来越成熟后，细分和验证会更可行，但这仍是未来几年里最有难度的治理问题之一。

这也解释了为什么测试要更严谨。现在只要“写完代码”还不够，必须知道是否真正满足预期指标。否则一旦模型误删代码，最粗暴的解决方式就是回滚一切。

软件工厂与组织重塑

Sonya Huang

我们再Zoom一下：你当初叫 Droid，后来改成 Factory。现在这个概念看起来普遍化了。你怎么定义今天的软件工厂距离终极形态有多远？

Matan Grinberg

可以说每家公司都已经有软件工厂，只是低效地靠经验和人力运行。10000 人以上公司里，feature 决策和发布链条会很长、很复杂，很多关键知识依赖经验丰富的“老人”。

AI 系统能把大量组织隐性知识显式化：审批、历史规范、流程步骤这些都可编码和复用。这样大家才知道到底哪些输入决定了功能优先级：客户信号、市场信号、产品负责人信号。

下一步是把软件交付映射成更像 assembly line（装配线）的流程，闭环回答：这次决策到底带来了业务结果。两年后，这种问法会让“按感觉加人/减人”变得过时。

Pat Grady

你刚才提到像 Mad Men 时代的营销，现在听上去很像缺了指标才会变成拍脑袋。

Matan Grinberg

是这个意思。像 Jack Dorsey 讲的“公司像 AGI”，我们也要像优化模型那样优化组织：哪一类节点承载最重要功能，哪些节点是负担，在哪里该加 token、在哪里该增人。

在组织层面，很多人还是靠‘感觉’调预算：比如随手裁员 2 万人。软件工厂的意义就在于避免这种拍脑袋，建立更可计算的分配框架。

Sonya Huang

那这会改变“每个 token 与人力”的分配吗？

Matan Grinberg

完全会改变。销售岗更擅长人际交流，少量 token 足够；工程岗如果拿到足够高质量 token，产出会有级别提升。财务、运营、营销等中间部门也会有介于其间的 token 与人力平衡。

很多公司起初尝试自建开发智能体，发现不是自己的核心竞争力。就像披萨店不需要自己建网站：市场上有工具可以做到同样效果。公司需要更狠地回归核心能力。

Pat Grady

这和之前的数字化转型有些像，但更贴近工程流程。你看到客户在重塑组织时有什么有效动作？

Matan Grinberg

我们观察到效果较好的模式是公司级 hackathon。给全员一个集中时间，强制尝试 AI 工作流。即使第一次失败也要承认失败，不追求‘第一天就一次到位’。从内部试错，通常比只靠管理层拍板更有效。

成功组织通常不会把“圣杯流程”神圣化。先试、失败、修正、再试。来自组织内部的倡导比高层硬性下发更容易落地。

Sonya Huang

再看下一年？

Matan Grinberg

我认为未来 12 到 24 个月，约 90% token 将是异步 token。意味着多数场景是智能体被动触发：发现客户信号后自动修复、先给一版草案。现在还是 Copilot 模式，任务还是用户先发起；但很快会更多像 agent-native（智能体原生）工作。

我经常拿 Tesla 工厂打比方：机械臂在黑箱中持续运转，名字叫 Dark Factory 也不是没有道理。我们的愿景是软件开发也朝这个方向走，流程像“机器造机器”。

Pat Grady

对未来最乐观的版本是什么？

Matan Grinberg

短期我预期行业会有震荡，很多企业多年资源配置明显偏离了效率，调整成本会很高，岗位会有压力。但我更乐观看待中长期：世界仍有大量问题没被软件化。工程师并不会消失，而会被释放去做以前未被解决的难题。

这也意味着更多高价值问题可以用更好的软件来解决，比如政府流程体验长期不友好、药物研发里的工程复杂度等。把顶尖工程师从低效劳动中解放出来，本身就是对行业的加分。

Sonya Huang

这段时间你自己的成长线也非常明显，Vision 十分稳定，而且公司规模也明显扩大。谢谢你今天分享，Matan。

Matan Grinberg

很高兴来分享，也谢谢你们。

Pat Grady

谢谢。
