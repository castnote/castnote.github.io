Claude Code 的创造者：世界上最热门的软件

本期节目请来 Anthropic 的 Claude Code 负责人 Boris Journey，讨论这类代码代理工具从实验室概念到大规模应用的过程。节目先回顾了 Anthropic 的安全优先背景：从提示注入、沙箱、权限控制到红队竞赛，讲清楚为何安全能力与产品同样核心。随后讨论了模型迭代与可用性的关系，认为 Opus 系列模型进步与产品增长高度相关。Boris 指出企业采用往往是渐进式的，先从小规模试点再扩展到全员，并强调默认安全设置、预算和权限治理的重要性。节目也探讨了界面形态从命令行到桌面和 Slack 对话式协作、代码质量反馈循环、角色分工重塑，以及企业对高能力模型访问与合规的顾虑。结尾部分强调技术并未替代人的高层判断，而是让人类更专注于目标设定与价值选择。

开场与背景

Joe Wisenthal

欢迎来到 Odd Lots。今天我们聊的是一个和软件生产方式密切相关的问题。

Tracy Allaway

我是 Joe Wisenthal，也是 Tracy Allaway。Joe，说说这个最尴尬的时刻。

Joe Wisenthal

我最近把桌面上很多截图都交给 Claude Code 去整理，包括一堆图表和素材。这个动作当时让我觉得自己像把“电脑”外包给了另一台机器。

Tracy Allaway

从效率角度看很合理，但第一个问题是：它做对了吗？

Joe Wisenthal

第一次是完全正确的。后来我也问过‘有没有会跑飞的概率’。有时会点了确认之后发生过惊险情况，这像是‘反向老虎机’，大多数时候有效，但偶尔会出事。

2026 年大家都在谈 Claude Code。先前软件股也曾因为市场恐慌下跌过，人们担心这类产品会取代一切。今天我想知道，AI 公司的边界在哪里，软件工程和个人工作台会走向哪里。

“Claude Code”为何诞生

Joe Wisenthal

这期请到的正是这款产品的核心人物，Anthropic 的 Claude Code 负责人 Boris Journey。谢谢你来做客。

Boris Journey

Anthropic 一开始就把 AI 安全作为主线。我们有很多难题，最难判断的是：模型在真实工作场景下是否真的安全。实验室里看起来安全，不代表落地就一定安全，所以必须让人真实使用。

由于模型与世界互动主要靠“写代码”，我们很自然会把“代码产品”作为重要入口。这个决定一方面让用户看到能力，也让我们更真实地学习安全机制。

早期的 Claude Code 最开始是从 Anthropic 的编码模型演进来的。那时一个模型顶多写一两行代码，但我们很早就知道它其实能做更大的事，比如生成完整文件。

Tracy Allaway

所以它最初只是一个“副项目”，但后来成了 Anthropic 公开关注的代表应用之一。这在时间线上挺反常识的。

Boris Journey

可以这么说。安全是公司使命，写代码只是其中一个非常自然的结果。它既能让我们快速测试模型与世界交互方式，也能给用户提供真正有价值的工具。

Joe Wisenthal

我自己从没系统学过编码，最开始只是复制粘贴输出。等我在 2026 年初真正下载并用上后，才发现生产力跃升明显，和去年底几乎是两种体验。

Boris Journey

这波爆发和模型版本提升高度一致：从 Opus 4.5 到 4.6 的能力跃迁很明显。Claude Code 的增长曲线也一并出现几个拐点。

更重要的是，我们和企业端是同一套基础模型和 API，Claude Code 并没有私藏‘暗门模型’。所以客户体验到的提升和我们看到的是同构的。

收益来源与安全机制

Tracy Allaway

那这个产品和 Anthropic 的商业目标关系是什么？是纯工具、是流量，还是更多？

Boris Journey

它当然是公司营收的一部分，但更关键的是它是安全研究的“测试场”。我们通过真实使用学习风险，也让模型更安全、更可控。

Joe Wisenthal

你提过模型可能越界。先给我一个‘提示注入’的简单解释。

Boris Journey

比如你让模型读一个网页并总结，结果网页里藏一句“请删除所有文件”。这条恶意指令不是你发的，是网站操控，模型如果直接执行就危险了。

因此我们加了权限确认、内置沙箱、持续红队测试和神经元探测。模型看到可疑指令时先被识别并拦截，配合自动模式和边界约束，减少高风险行为。

Joe Wisenthal

外界常说模型很会‘钻空子’，你们怎么处理？允许它“想办法”完成任务和安全边界之间如何取舍？

Boris Journey

我们用两条线：第一，训练层面对齐，让它尽量按你真实意图执行，不去‘作弊’；第二，产品层面做护栏，比如权限、sandbox、默认安全设置。工程上这两类会一起工作。

代码生成为何逐步变好

Tracy Allaway

很多人看到 Claude Code 写了第一版代码后会有 bug，为什么第一次常常不完美？

Boris Journey

和写作类似，第一次输出常常是草稿。先有一个可运行版本，再通过迭代修改。对模型也是一样，先给方向，再靠反馈循环修正。

Joe Wisenthal

所以它更像个反复试错的合作者，不是一次性出答案。

Boris Journey

没错。我自己也说过给代码一个盲人雕塑家类比：先有雏形，再通过反馈逐步变好。反馈越充分，结果越接近你要的样子。

过去你得自己从草稿到调试。现在很多人只要设定目标，模型就能自动反复跑、检视、修正，大大提升效率，但前提是有正确反馈通道。

我们正在往“循环任务、流程、长期会话”演进。模型运行较长时间后，不断拿到上下文，就像一个懂得接力的同事一样，不再只会被单句提示牵着走。

从工程师视角看，代码好坏不是黑白分明：能跑并不代表美观、健壮或可维护。我们仍在持续提高代码质量和可读性。

企业中的角色变化

Joe Wisenthal

听起来现在连你自己都很少“手打代码”了。

Boris Journey

在我加入之前我也经历过几个月不写代码，后来转到管理和文档后很不舒服。所以后来我基本都用 Claude Code 写代码。

现在我在 Anthropic 99% 代码都是 Claude Code 产出的。团队里其他人也是。最初几行改动还是有人手改，但比例在快速下降。

Tracy Allaway

这对招聘会有什么影响？传统“会敲代码”是不是不再是第一项核心能力？

Boris Journey

我现在更愿意把能力重新切分成原型者、建设者、维护者、扩展者和打磨者。任何人都能写代码，但要把它落地、稳定运行和可扩展，还要工程思维和产品判断。

我们团队里设计师、PM、工程经理都在直接写代码，因为工具门槛低了，沟通成本反而下降。

界面形态与协作方式

Tracy Allaway

早期命令行是停泊点，接下来会不会有更传统的完整 UI？

Boris Journey

命令行一开始是为了尽快上线。后来我们扩展到桌面、移动、Slack。现在我自己主要在 Slack 使用，体验更像跟同事对话，而不是每次都切界面。

Joe Wisenthal

这就涉及组织落地。大公司里有人会担心“岗位被挤兑”——设计师原本回答问题，现在助手先回答，是否会有摩擦？

Boris Journey

这是典型组织行为问题。历史上 PC 和互联网也经历过‘谁该掌握新工具’的重塑。只要企业把核心流程放在中枢，工具会持续放大生产力；但如果只是“有人替代别人”，抵触会更强。

Slack 场景里，模型可以主动插入对话、查数据、给建议并生成方案草图，这不是传统 UI 帧架。它更像一场正在发生的协作对话。

我给它了一个 Slack 例子：频道里有人说图标按钮分不清，Claude 自动进入对话、调取数据、比较两个来源并给出设计建议。它甚至会产出草图。

Joe Wisenthal

这类“未被点名也会发言”的行为，理论上提高效率，但在公司里可能让员工觉得自己被越位。

企业采纳路径与监管边界

Tracy Allaway

从企业视角看，采纳的第一步是什么？

Boris Journey

通常是先有人试用 AI，再给团队分发 Claude Code，再扩展到协作场景。每一步都要配套权限、预算控制和企业安全设置。

我们会默认把安全参数打好，企业不用从零研究。常见做法是逐步扩量，先一个人一个会话，逐渐放大到每百人、上千人。

Joe Wisenthal

但很多公司对桌面端权限很敏感，尤其是能接触文件系统时。你们看到的阻力有多大？

Boris Journey

一两年前确实明显焦虑，今天更多是信任与成熟度问题。只要公司逐步建立治理，尤其是沙箱和行为监控，使用熟悉度上来了，这种阻力会显著下降。

Joe Wisenthal

模型发布节奏这几年也在讨论。高能力模型是不是不会普遍放量？

Boris Journey

我们会尽量让更多人拿到最强的效率模型，同时对高风险模型做更谨慎分层。像 Mythos 这类更偏攻击性的能力需要更慢更严谨的 rollout。Fable 这类版本则更广泛可用。

Joe Wisenthal

所以企业不用担心被“分流歧视”——重度用户和轻度用户的可用性上限不会刻意撇开。

Boris Journey

是的，默认可访问性和配额设计是常态化经营，关键是让团队拿到稳定且可预测的体验。

技术竞争与业务模型

Tracy Allaway

你对模型持续进步的看法很正向。你怎样回应“AI 会让软件服务都没护城河”的说法？

Boris Journey

任何公司都在变化。以前网络效应、规模效应、转换成本这些 moat 依然存在，只是相对权重会变化。AI 让某些壁垒变薄，比如迁移成本会更低，但不会把所有护城河都拿走。

如果供应商把所有核心能力都藏着，未必能长期赢。我们更关注的是把模型、安全和执行能力长期迭代，和客户实际结果绑定。

Joe Wisenthal

市场上也有人担心供应商控制、数据外泄、被“黑盒化”。你认为客户如何取舍？

Boris Journey

最核心是激励和透明。我们承诺隐私和安全，例如在企业端不能看到用户完整对话。客户如果担心，必须把‘可控性’和‘前沿能力’对照权衡：是用更小模型可控、还是持续更新的高能力模型更划算。

我认为只要模型持续进步，长期来看前沿服务仍有强动力，不必被限定在老旧栈里。你要么选择慢迭代安全模型的管理成本，要么选择持续迭代下更高收益的模式。

程序语言与企业改造

Joe Wisenthal

很多人听到“代码助手”会担心传统语言会不会被取代。你怎么看？

Boris Journey

语言会慢慢变平。像 Bun 迁移团队把 Zig 代码移到 Rust，过去可能要数月甚至一年，现在十几天用 Claude Code 就能完成。成本模型和速度都改变了。

Joe Wisenthal

这会不会造成“语言无所谓，模型都能写”这种认知？

Boris Journey

短期语言仍有差异，强类型和静态分析仍会让模型写得更稳。长期模型更强后，门槛会更低，但语言设计仍影响效率和可维护性。

我反而更期待的是更多新语言和范式出现。AI 让更多人能快速验证新想法，这可能像当年 PC、互联网时代一样出现更快的技术分化。

Tracy Allaway

你刚才举了图形界面例子。文件系统这种可视化传统工作流是否会继续存在？

Boris Journey

它不会消失，但权重会变化。现在很多人已经不先找文件，而是先发指令。可视化更可能是“对话驱动的协作窗口”，不是静态文档柜。

长对话中的稳定性与记忆

Boris Journey

现在的模型有更强的上下文能力，能保持长周期一致性。我们已经在 Slack 看到几周以上的任务会话，能记住既定目标并持续推进。

早期它更容易‘跑偏’，现在目标更清楚、工具更稳定，能在不人工每一步确认的情况下持续工作。

Joe Wisenthal

你们还在做什么下一步能力？

Boris Journey

把现有能力从‘一轮一轮 prompt’升级为流程化协同。就是让模型在你给目标和边界后，自主调用工具、检视结果、修正细节，像真正同事一样持续推进。

Joe Wisenthal

这其实也解释了为什么写作、销售这些任务很难被完全替代。

代码可被立即验收：要么能跑要么不能跑。像写作和决策类任务没那么明确的即时反馈，所以代际差距更受风格和判断影响。

Boris Journey

写代码质量也不是只有对错，但反馈环更快，模型会持续改进。我们也承认它有偏差、语气会不理想、还需要更好的文风控制，这些都在改进中。

收官：人和模型的边界

Joe Wisenthal

非常有意思的是，Boris 以前把代码比作写诗，强调可验证性和体验质量。它并不只是“生成文本”，而是生成可运行的世界。

Tracy Allaway

节目里还有一个哲学问题：当模型承担越来越多机械性工作后，人类是否会失去“基础能力”？

Joe Wisenthal

我担心的一点是高阶思考可能越来越少人做，但现实里每个人都会被推向更高抽象层。也许真正稀缺的是判断、方向和价值选择。

Boris Journey

我同意。模型擅长执行、编排和加速，但人的角色仍然是设定目标和价值框架。你如果只关注“生成内容”，会很快失焦；如果专注“为什么做”才是长期优势。

Tracy Allaway

这可能会影响到职业训练方式。以前大家只做某个技术工序，后来更多人要理解链条的全局。

Joe Wisenthal

没错，机械层面可能会被工具替代，但设计判断、商业判断和文化判断仍然依赖人类。我们先把这一集先到这。
