**Kent Beck**

这门语言是什么样的？Dan Ingalls 有一篇很漂亮的论文，叫 The Design Principles Behind Smalltalk。开头一句是：Smalltalk 是为每个人的创造精神提供计算机支持。

这里有两条大主线。一个是编程语言，也就是 Smalltalk 语言；另一个是交互语言。重叠窗口、作为指点设备的鼠标、窗格、滚动条，这些都是从用户界面里开创出来的东西。

这些东西今天看起来很普通，但 Smalltalk 这门语言本身，是由极少数原语构建出来的。语言里真正只有三个原语：发送消息、给变量赋值、返回一个值。基本就这些。

我觉得美的地方在于，这门语言把自己的机制推到了极限。Smalltalk 里一切都是对象，包括数字。你不是调用一个函数来把两个整数相加，而是发送一个 plus 消息，由一个整数接收，并把另一个对象作为参数。

如果另一个对象碰巧也是整数，那就把它们加起来。这会带来一些有趣的结果，比如语言本身没有定义控制结构。所以 if then else 不是语言的一部分，而是库的一部分。

你把 if true 这个消息和一个闭包发给 true，它就求值这个闭包；你把 if true 和一个闭包发给 false，它什么也不做，只是返回。所有东西都是建立在同一种基底上。

Smalltalk 里的特殊情况非常少，这意味着有时你得动点脑筋，才能理解条件语句是怎么工作的。但等到你要构建抽象时，也不会有一堆特殊情况挡在路上。

我们也许早该提到 OOPSLA。那是一个非常火的会议，重要人物都会去，而且增长很快。我算是误打误撞参与进去的。1989 年，我担任 OOPSLA 的程序主席。

我花了一个月只读论文，完全忽略了 Playground 项目的职责。那差不多就是压垮骆驼的最后一根稻草。他们说，好吧，你没有在帮我们，所以你需要离开。

然后会议举行了，而我的第二个孩子正忙着迟迟不出生，所以我甚至没能去参加那场会议。

不过我之前听说了 Playground 项目，于是转到了那里，做了一点工作，帮助构建这门给孩子用的编程语言。它是超越面向对象编程（object-oriented programming）的下一步。

今天你会把它叫作响应式编程（reactive programming）。你不能发送消息，只能触发某个条件，而另一个对象正在等待这个条件。它有点像发布订阅（PubSub），但那是唯一的控制机制。

**Gergely Orosz**

我还想问你，大概也是这个时期，出现了 CRC 卡。CRC 卡是什么？我知道它代表类、职责、协作者卡（Class Responsibility Collaborator cards），但它们是什么？你们又是怎么想出来的？

**Kent Beck**

你有这些命令式程序，也有流程图。流程图虽然有点啰嗦，但能准确表示命令式程序里的控制流。现在我们有了对象，你会发送具有多态性的消息。

所以当你发送一条消息时，你并不知道到底会调用哪段代码。人们就会问，那你怎么把它可视化，怎么把它内化理解？

对我来说，我有动觉联觉。所以当我看代码时，能在身体里感觉到它想往这个方向走，它是……是的。我不知道是否见过其他人也用类似方式描述自己的编程体验，但就是这样。

问题是，不管你用什么方式内化理解，怎样才能感知这个程序里发生了什么？因为你不能只说，我们执行这一行，然后执行那一行。只要发送一条消息，我们就不知道接下来会发生什么。

于是 Ward 想出一个主意，把正在发生的事情写在卡片上，也就是索引卡。因为我们平时总是这样交流。

比如，我们得有一个矩形，它要求渲染器做某件事，然后它进入管线，接着如何如何。所以我们说话时经常用手比划。

于是他说，为什么不把这些东西写在卡片上？面向对象编程里的一个巨大挑战，就是划分职责。

因为你是在把计算移动到数据所在的位置。说这个对象做这件事，那个对象做那件事，是非常关键的决策。你希望计算靠近数据，这样它们之间的耦合就会更少。

**Gergely Orosz**

我觉得这个经验在噪音中有点被遗失了。

**Kent Beck**

这是设计面向对象程序时最根本的设计动作。我认为我仍然支持这个观点。

**Gergely Orosz**

所以是让数据靠近它被使用的地方？

**Kent Beck**

也就是计算发生的地方。不，反过来。让计算移动到数据已经存在的地方。让计算移动到数据所在的位置。

**Gergely Orosz**

比如，如果你有一个富对象，里面有很多数据，你希望计算移动到那里。所以你希望对象被调用后，直接取得数据，并完成它们需要的计算。

**Kent Beck**

如果我要操作矩形内部的东西，比如面积，我是把“高乘以宽”散落到系统各处吗？还是在矩形内部放一个 area，由它来处理高和宽？走到极致时，我就不再关心矩形是否有高和宽了。

这些细节对外部世界是隐藏的。我可以用两个角来表示矩形，也可以用左上角、高度和宽度来表示矩形。对外部世界来说，只要它们都能响应 area，就没有区别。

于是我可以提出一种新的表示方式，再提出另一种表示方式，而外部世界不必关心。如果我把计算移到了数据所在的地方，情况就是这样。

**Gergely Orosz**

是的。也就是说，你可以获得更松的耦合。

**Kent Beck**

没错。

**Gergely Orosz**

明白了。这是一个很好的经验。

**Kent Beck**

是的。

**Gergely Orosz**

是的。即使在今天也一样，因为我们做的几乎所有事情底层都有对象，或者很大一部分是面向对象的。而我觉得我们并不会经常思考这些。

**Kent Beck**

是的。我看到很多对用面向对象语言写出来的程序的批评，但那些批评并不是针对面向对象编程或面向对象设计本身的。

**Gergely Orosz**

在 Apple 之后，你去了一个叫 Masspar 的公司。我在这里注意到的是单元测试。据我理解，你是在 Tektronix 时提出了一个叫 SUnit 的东西。

**Kent Beck**

我那时开始对测试感兴趣。当时，测试是一条社会学上的分界线。如果你在计算机科学学校拿 A 或 B，你就去写程序；如果你拿 C，你就得当测试员。

所以那确实是一种身份地位的区分。我不会去测试，我是这边的人，不是那边的人。但我开始感兴趣的是，怎样自动测试程序？怎样对自己正在做的事情建立信心？

我本来就容易焦虑，而程序越复杂，我需要担心的东西就越多。我对可能存在的 bug 类型越有经验，就越焦虑。于是我想，应该有某种办法能不靠药片来平息这种焦虑。

**Gergely Orosz**

那就太好了。

**Kent Beck**

我尝试了很多编写自动化测试的方法。当时除了这种身份分界，还有工具分界。你有各种测试工具，它们通常会有某种自己的语言，用来连接被测程序。

所以我试了这个、那个，还有别的东西。其实是在 Masspar 之后。那都是远古史了，我们得去挖考古地层才能说清楚。

后来我开始做咨询，准备告诉一个客户他们应该写测试。我第二天要飞去 Chicago，但当时还没有办法让他们写测试。

于是我把自己做过的五六个实验综合起来，形成了 test case、test suite 和 test result。基本上就是三个类和十二个方法。

但它是一个框架，你可以用它编写测试，让测试彼此隔离地执行、完全自动化运行，并给出结果汇总。

**Gergely Orosz**

所以这基本上就是一个面向 Smalltalk 的单元测试框架，对吗？

**Kent Beck**

是的，第一个版本是用 Smalltalk 写的。Masspar 是一家 Silicon Valley 初创公司，拿了风险投资，目标是构建一种全新的架构，也就是 SIMD，单指令多数据。

我们会有一个由处理单元组成的环面，最多 16000 个处理单元。也就是说有 16000 个处理单元，它们连接成一个环面网格。

你可以和左、右、上、下以及对角线方向的处理单元通信。它现在看起来很像 NVIDIA 的架构。但那是很早以前，实在太早了。

我在那里花了三年，为高性能计算构建编程环境。目标是获得当时 Cray 那类机器的性能，但成本只有十分之一。

他们需要一个编程环境。所以我们用 Smalltalk 构建了一个编程环境，里面有一些非常酷的东西。你可以单步执行 Fortran 程序，同时构建性能剖析。

**Gergely Orosz**

不会吧。所以你们构建了一个运行时，让你们可以在 Smalltalk 里做这件事，比如解释 Fortran 程序并运行它们。

**Kent Beck**

不是。我们有标准编译器，一个优化编译器。但因为我们控制了操作系统，所以可以构建非常底层的探针来收集性能剖析数据。

所以，对于这些运行在 16000 个处理器和海量数据上的 Fortran 程序，我们可以拿到行级别的性能剖析。

**Gergely Orosz**

太厉害了。当你从不只是……

**Kent Beck**

就像你在往更底层走，构建那种运行程序的基础设施。

**Gergely Orosz**

但我想回到 SUnit。SUnit 的概念，也就是你组合起来的这些概念，test case，还有什么来着？test case、test suite 和 test result。

这套东西真的留下来了。后来有 JUnit，那是你之后和 Eric Gamma 一起创建的。然后还有一整套，比如 NUnit，我想那是给 .NET 的，还有 xUnit.net。

它们都继承了其中一些想法，很多现代单元测试框架也是建立在这些想法之上的。你为什么认为它这么有生命力？又为什么觉得它之前没有被创造出来？

**Kent Beck**

之前没有出现，是因为程序员和测试员之间有这种社会分界。测试员很有动力拥有自己的语言：这是我的工具，我知道怎么运行它，我来运行它。

而且那时双方关系也很对立，还有点居高临下。比如，你是程序员，不能信任你来测试，你只会说它运行得很好。我要来做成年人监督。

有时候程序员确实会那么做，所以也很难反驳。但我认为这强化了一种观念：测试工具是它自己的世界。

那个有启发性的决定，是用与被测对象相同的语言来写测试。这对我来说是很自然的决定，因为我在用 Smalltalk，而任何东西都应该能在 Smalltalk 里表示。

**Gergely Orosz**

也就是说，你已经习惯了问：我怎样把这个表示成对象？听起来 Smalltalk 这门语言在很多事情上都很早。

我感觉很多创新都来自 Smalltalk，因为它是最早拥有对象的语言之一，但它又是一门非常简单的语言。所以你需要构建很多东西。

这又促使人们去表示很多东西、讨论它们，产生设计模式，现在还包括能够编写自己的测试环境，或者说如果你想做这件事，就被迫这么做。

**Kent Beck**

嗯，Smalltalk 背后有一种精神。如果你不喜欢工具，比如你正在运行调试器，而调试器缺少你此刻真的需要的某个功能，你就直接跳到栈上，实现你想要的功能。

然后你再回到原本正在做的事情。这是非常自然的，因为从来没有那种巨大的鸿沟。想象一下今天我在用 C 编译器，然后意识到，哦，我希望 C 有这个新特性。

那就等于是启动一个多年项目，要跨到下一层级有非常高的进入门槛。而 Smalltalk 在设计上不是这样。比如你有弹出菜单，能直接看到所有选项。

这是一个有意的教学选择。它在说，好吧，你知道剪切和粘贴，但你不知道在这里还能做的其他事情。所以菜单不只是给你剪切和粘贴。

它把你能做的所有事情都给出来，用这种方式鼓励你学习它们。因为你最终会看到这里有一个 format 项。

**Gergely Orosz**

然后我会说，嗯，这个是做什么的？

**Kent Beck**

所以，系统会在你持续使用它的过程中教你，这非常属于 Smalltalk 的精神。因此，用这门语言来构建测试工具是很自然的。

当然，你也必须稍微扭曲一下这门语言。这里有一个用于某个 test case 的类，里面有一个方法代表其中一个测试用例，并且它以 TEST 开头，这有点魔法。

这就开始变得有些黏糊了。执行时，你创建这些对象中的一个，给它发送 setup，因为你不知道，可能需要先构建一些东西。

然后你给它发送那个 TEST 开头的测试方法，它执行那一件事。接着，无论结果如何，你都会从那里运行 teardown。

所以它看起来语法和语言本身一样。测试的表示形式，有点借用了普通代码的表示形式，然后你再自己解释它。

所以它在语言里，但同时又不完全在语言里。只是人们不会这么想。他们只会想，我继承这个类，给一个带 test 注解的方法，或者以 TST 开头的方法，然后它就能工作了，这就够了。

**Gergely Orosz**

我想跳到几年后的 1996 年。你开始参与 Chrysler 的一个项目，也是在那里你遇到了 Martin Fowler。那是一个什么项目？

**Kent Beck**

其实我在那之前稍早一点就见过 Martin Fowler。早在第一批 OOPSLA 会议上，大家就在问：我们怎样以不同于上一代工具的方式，管理使用对象的项目？

上一代工具给你的变更选项明显少得多。你仍然必须改代码，但相比使用面向对象程序，那要困难得多。

所以方法论是什么？我们当时有结构化分析、结构化设计。那么对象的方法论是什么？它应该有什么不同？这是最初 1986 年 OOPSLA 上价值百万美元的问题。

到 1994、1995 年左右，我们开始有点明白它会是什么样子。

我想 Rational Unified Process，或者后来会进入 Rational Unified Process 的那些东西，在那时已经存在了。Grady Booch 参与其中，还有 Ivar Jacobson、James Rumbaugh。

结果证明，每个人都是这样。你可以在 Ward 的 C2 网站上找到 Episodes。把它拿来比较非常有意思，因为我从那里借用了很多东西。

当时在 Snowbird 举办了几场关于方法论问题的工作坊。我不知道为什么我们选 Snowbird，是别人选的。我是在自己参加的第一场工作坊上遇到 Martin 的。

我记得第一次做关于 XP 的演讲时，我带了一些传单发给大家。我想那是在 Uppsala，一个小组讨论还是什么场合。我讲了一些 XP。结束后，人们都来拉着我要一份。

他们对它的反应就是拽着我的衬衫，想要从这个东西里拿到一块。我觉得 XP 的时机非常精妙。.com 的上行期，也就是不是泡沫破裂，而是上升那一面，刚开始显现。

他们看其他方法论，会说要非常仔细地准备，做这个分析文档，做那个设计文档，然后大量编码，再大量测试。他们能看出来，在互联网浪潮开始抬头、进入超高速增长的世界里，这行不通。

另一方面，我们也知道那种牛仔式做法也行不通。就是有 Jolt Cola，愿它安息，有一群程序员，做些别人看不懂的东西，不跟任何人说话。你只要从门缝里塞披萨进去，然后等代码出来。

那也不会奏效。而这里有个东西，看起来介于两者之间。它有纪律，有迭代，有透明度。你有办法掌控正在发生的事，也有办法调整流程。

你有所有这些测试，确保东西真的能工作。人与人之间也会频繁对齐，无论是业务人员和技术人员，还是技术人员之间。于是大家会想，好，我能看出这可能有效。

所以他们看到互联网正在爆炸式增长，而我可以用 XP 抓住这个机会，采用其他方式却做不到。实际上，当时也没有真正的替代方案。

**Gergely Orosz**

基本上，XP 给了你一种方式，可以相当快速、灵活地前进，同时又有稳定感，而不是彻底失控。你有测试，有迭代，有计划，有学习。

那测试驱动开发（Test-Driven Development, TDD）是什么时候出现的？你后来写了一本书，好像两年后出版，叫 Test Driven Development by Example。它和 XP 的关系是什么？

**Kent Beck**

对我来说，测试驱动开发是更早的一次重新发现。记得我小时候读了很多书。我还记得我爸带回家的一本书，至今我都没找到它的副本，里面写着：你应该这样编程。

那还是磁带到磁带的时代。你会有一卷输入磁带，类似工时卡，然后把它送进薪资程序，程序会写出一卷输出磁带，里面是支票金额、代扣款等等。

所以一直都是这样。那真是很早很早以前，你会有一长串这样的东西。它其实是函数式编程，因为你不能修改输入磁带。

处理薪资、应付账款或库存，就是一个流程：我拿这些磁带，喂给这个程序；把它的输出拿来，再喂给下一个程序，然后如此反复。

**Gergely Orosz**

真的是手工操作？实际把一卷磁带取下来，再挪到另一个地方？

**Kent Beck**

对。那本书说，写这种程序的方法是：拿一卷输入磁带，一卷你确实需要处理的真实输入磁带，然后手工输入你期望它生成的输出磁带。

你会说，好，这个工时数应该在输出里产生这样一条记录。

**Gergely Orosz**

我明白这要引向哪里了。你是在先定义输出，在开始写程序之前。也就是说，你首先要知道自己期待什么，以及如何验证它。

**Kent Beck**

没错。我小时候读过这个，但完全不懂。可它一直留在脑子后面某个地方。我写了 S-Unit，开始使用它，然后把它给了 Hal Hildebrand，他是我认识的最聪明的程序员之一。

我本来觉得他不会需要它。但他用了，而且很喜欢。所以我知道这个测试框架有点东西。后来我只是在随便琢磨，又想起了先输入输出磁带这件事。

我把它映射到自己用 S-Unit 做的测试上，然后意识到，如果我遵循这个模式，就会在写代码之前先写测试。我记得自己当时大笑出声，因为这想法太蠢了。

为什么要写一个你明知道会失败的测试？类都还没定义，方法也还没定义。它在可能成功之前，会以一堆不同方式失败。好啊，那就试试看会发生什么。

我第一个例子用的是栈。创建一个新栈，压入某个东西，再弹出来，我应该拿回同一个东西。好，然后我去实现它。不行。好吧，这很容易满足。下一个是什么？

你压入两个东西，然后按正确顺序把它们拿回来。好。接着是这个、那个，重复项、pop、top、isEmpty，然后结束。焦虑去哪了？哦，没了。

**Gergely Orosz**

第一次就这样？哇。你想不出另一个不会通过的测试用例了。

**Kent Beck**

所以我真的完成了。我觉得自己完成了，而且感觉很好。我确实完成了。

**Gergely Orosz**

哇。从“这是个蠢主意”到“我们试试看”。

**Kent Beck**

绝对是。我有个评论：永远试试你的蠢主意，前提是成本低，而且可逆。从桥上跳下去不是可逆决定。

**Gergely Orosz**

我说的不是那种。我说的是这种事：你只是想，这里有个蠢主意。

**Kent Beck**

一百次里有九十九次它会失败，但剩下那一次你不会有任何竞争者，因为其他人都没蠢到去试这个想法。这种朋克态度的一部分，就是我不在乎你怎么看。

这让我能够尝试大量蠢主意。大多数你们都看不到，但其中有一串结果远远好过人们本来预期的那些。

**Gergely Orosz**

然后还有一群人也尝试了这些想法。我觉得测试驱动开发（Test-Driven Development, TDD）就是个好例子。有一段时间，在你写了那本关于 TDD 的书之后不久，它非常流行。

我到现在还记得，2000 年代末我应该也有一本。人们会做小组练习，开发者也会照着这种方式开发。随着时间推移，它的热度大概明显下降了。

我会说到了 2010 年代，我看到做 TDD 的人越来越少，它几乎完全不流行了。现在随着智能体出现，这个想法又回来了，因为事实证明它也许更耗时，但智能体可以这么做。

而且让它们测试自己相当有用。短期看会消耗 token，但长期看可能会节省 token，因为经典的精灵式错误之一就是东西根本跑不起来。那么你怎么稍微收紧缰绳？TDD 又为什么会过时？

**Kent Beck**

我认为很大一部分原因是，我会在某件事上做一阵子，然后转去做别的事。模式（Patterns）是这样，JUnit 是这样，TDD 是这样，极限编程（Extreme Programming, XP）也是这样。我就是会走向下一件事。

所以我转向了下一件事，TDD 留在了那里。然后有些人把它当成道德大棒，比如你应该使用 TDD；如果你不用 TDD，你就不专业。这完全是胡扯。

人们可以用各种各样的工作流写出非常好的软件。当然，不同工作流各有利弊。TDD 的甜点区，是发现和实现的结合。

我大概知道自己想往哪里去，但不确切知道怎么到达那里。不过我知道第一步是什么，于是我迈出第一步，它教会我一些东西，让我能迈出下一步，然后又学到东西。

如果你能一路实现、实现、实现，那也很好，还有别的工作流也没问题。如果你只是坐在那里一直学习、学习、学习，我不认为那很有效，但你当然不一定需要 TDD。

真正适合 TDD 的，是你在“我做一件事，我学到一件事”之间快速交替。做一件事，学到一件事，再做一件事，再学到一件事。TDD 在这里非常强大。但这不是道德选择，而是实践选择。

**Gergely Orosz**

测试驱动开发是 Kent 对软件编写和交付方式最持久的贡献之一。今天，随着智能体开发出现，它比以往任何时候都更重要。

我想聊聊另一件你也非常出名的事。我记得有 17 个人参与撰写，但你排在第一位：敏捷宣言（Agile Manifesto）。你能带我回到 Snowbird 当时发生了什么吗？

那时行业是什么样的？又是什么让你们所有人聚到了一起？

**Kent Beck**

当时有一群人。还记得我们刚才在说，面向对象的方法论是什么。那时有一种占主导地位的 Rational Unified Process，我会说它既不 rational，也不 unified，更不是 process。

不过这是另一回事，我主要是故意刺激人。但那被认为是成年人做开发的方式。有一群人，如果你去问 Grady、Jim、Ivar 他们会怎么应用它，实际上看起来很像我会采用的开发方式。

但关键不在于你会怎么做，而在于那些读了你写的东西的人会怎么做。它当时被用成了非常瀑布式的风格：一大堆分析，一大堆设计，一大堆实现，单独测试，然后一遍又一遍地灾难。

所以我们一群人看着这种情况，各自以自己的方式、在各自的时间顺序里说，不，我们不该这么做，我们应该做点别的。我们开始发出足够大的声音，于是开始被 Rational Unified Process 那些人攻击。

他们的意思是：你不该那么做，你应该做我的这一套，而且我还会卖给你几百万美元的工具来帮你这么做。我能理解他们为什么会攻击我们。

但我们开始意识到，如果我们都在朝类似方向前进，Scrum、特性驱动开发（feature-driven development）这些人就必须走到一起。我们在挪威开过一次会，大家聚在一起做了演讲。

那是在我住在欧洲的末期。我在瑞士住了两年，1997 到 1999 年。所以在 1999 年，我们飞到挪威北端，坐上 Hurtigruten 渡轮。这个名字我练过发音，但肯定还是说糟了。

我们坐这艘渡轮一路到 Bergen。那里整天整夜都是亮的。这绝对是人生清单项目，如果你有机会一定要坐，因为风景实在壮观。

但我们当时开会讨论的是：我们之间有没有足够多的共同点，真的可以一起做点事？那次会议的感觉是，是的，我们应该一起做点事，但仍然有很多摩擦，也有很多分歧。

**Gergely Orosz**

你说的是一群自尊心相当健康的人，而且都有强烈观点。

**Kent Beck**

包括我，而且我的自尊心在里面绝不算小。所以回来之后，Jim Highsmith 和 Alistair Coburn 又在 Snowbird 召集了一次会议。我们之前已经在那里开过一阵子这类方法论会议。

于是我们都去了。其他人讲过那次会议的细节，我没法准确回忆，所以可以去找那些回忆记录。但对我个人来说，那次会议并不顺利。

我当时得了严重的鼻窦感染，吃着很强的药，所以总体上我不太记得会议内容。但我知道事情进展不太好，因为所有人都在说，我想把我的东西写进去；不，我想把我的东西写进去，而那又和你的东西矛盾。

于是大家休息了一下，走了出去。Martin 和 Jim Highsmith 留在了屋里。等我们休息后回来，宣言的基本结构已经在那里了。

就是那种格式：我们重视这些东西，但我们更重视这些东西。四个具体条目也都已经定下来了。那是一个神奇时刻，而我对此没有任何贡献。

**Gergely Orosz**

然后你们又提出了那些原则。

**Kent Beck**

我记得里面唯一属于我的词，是谈到与用户每日互动时的那个“每日”。

**Gergely Orosz**

我觉得我在里面没有别的贡献了。

**Kent Beck**

但到发布的时候，名字按什么顺序排列？是字母顺序，对吧？绝对是字母顺序。所以当有人说，哦，你是签署人之一，我会说，不，我是第一位签署人。按字母顺序。

**Gergely Orosz**

那敏捷宣言的影响是什么？

**Kent Beck**

立刻见效，立刻。人们非常兴奋。那时又一次，互联网泡沫破裂的低 rumble 已经出现了。Dot-com 当时还在上涨。

**Gergely Orosz**

我想是的。那已经接近尾声了。

**Kent Beck**

但肯定接近尾声了。可人们仍然在寻找一种答案：我们该怎么做？这些事该怎么做？我们怎么快速、便宜、可靠地构建软件？每个人都在寻找这个。

**Gergely Orosz**

还要带有可选性。

**Kent Beck**

对，带有可选性。因为当事情不确定时，选项恰恰能给你最大的价值。而我们有一套关于如何保留可选性的叙事。我们每个人都以各自不同的方式在讲。

那也是另一个案例。XP 是第一次有人拉着我的衣袖追问。JUnit 又是另一次，它来自 S-Unit。我有 S-Unit，Eric Gamma 当时在用一种新语言 Java。

我们一起飞去美国。他要给我展示 Java，我要给他展示 S-Unit。所以在从 Vienna 飞往 Washington Dulles 的航班上，我们开发了 JUnit，而且 JUnit 用自己测试自己。

**Gergely Orosz**

哇。

**Kent Beck**

等我们落地时，在飞机上没有互联网。没有互联网，电池只有两个半小时，时钟在滴答走，座位上也没有电源适配器。那简直像马车时代的计算。

我们落地后，把 JUnit 给了 Fowler，他当时也在 OOPSLA。第二天就有人来问，我听说你有一个 Java 测试框架，能给我一份吗？

于是我们制作软盘，三点五英寸软盘。我们以最快速度把它们发出去，因为需求太大了。所以那是我第二次经历那种情况。

**Gergely Orosz**

需求、产品市场契合。

**Kent Beck**

对，没错，产品市场契合。然后敏捷宣言就是下一版这种情况，人们真的为它感到兴奋。保留最初签署人的做法，是一件很漂亮的营销作品。之后如果你想签署，有一段时间也可以签。

**Gergely Orosz**

我想他们后来关闭了，因为人数太多了。

**Kent Beck**

对。但这意味着人们觉得自己投入其中了。他们已经买账，已经把自己的名字附在这件事上了。这不是很有意思吗？

**Gergely Orosz**

这种投入感，能够贡献或者感觉自己在贡献，确实会带来差异。它已经带来了差异。对敏捷来说肯定如此。

**Kent Beck**

有一个后续点是 agile 这个词。当时争论的一部分就是，我们到底该把这东西叫作什么。有人提议叫 agile，我不记得是谁，但大概有人知道。

我当时反对。这个词让我不喜欢的地方，当时不喜欢，现在也不喜欢，是它不可防守。没人会说，我不敏捷。

**Gergely Orosz**

哦不，我更喜欢僵硬开发。

**Kent Beck**

哦，我更喜欢不灵活开发。不，所有人都会说自己是敏捷的，而 extreme 没有这个问题。如果你努力打磨技能，能够结对，能够增量式设计，能够彻底测试，能够构建工具并做这些投入。

这时你说，好，我是一个极限程序员。如果你没有做这些投入，你绝不会在不是极限程序员的情况下说自己是极限程序员。但就算你绝对不是敏捷的，你也会说自己敏捷。

这就是我当年的反对理由。而后来事情也确实这样发展了。这个词现在不只是没有任何含义，它还带有负面含义。

**Gergely Orosz**

我们能聊聊敏捷的“身后世界”吗？还有大写 A 的 Agile 版本。围绕它已经长出了一个完整产业，最初本来是想做好事，但后来变成了卖蛇油的行业。

很多方面看，现在我们有各种规模化敏捷框架，被以高价卖给大型公司，你可以想象，它们反而用更多官僚流程拖慢这些公司。

你是怎么看到这一切发生的？你预料到 Agile 会变得这么大，既成为商业故事，又长出这些蛇油味很重的部分吗？

**Kent Beck**

当时我们把这些东西放在一起的时候，我确实担心这种情况会发生。敏捷宣言（Agile Manifesto）是当时房间里那些人的想法的交集。我认为软件开发里还有很多东西，并没有包含在宣言之中。

我写过一本又一本书，讲我认为那些东西是什么。没有技术能力作为基础，你可以有最好的意图，说我们能够重新规划，能够按任意顺序实现。我们有一组功能，可以随便先做哪一个，也可以随时加新功能。

你可以说你要这么做，但如果你没有技术功底，不能高效地、一点一点写出可靠软件，一点一点做设计，保留并增强可选性，在需要时自己写工具，那就做不到。这些事情在技术上都很难。

这就像第一次滑雪板，就把人放到雪崩顶端。你一路摔下山，把身体摔成好几处骨折，某种意义上也算敏捷。但这并不是我们说的敏捷。你需要那个基础。

可当时有人愿意说，不用担心，这很容易，你能做到，任何人都能做到。用一半时间完成两倍工作。从我的角度看，这就是谎言。

你能不能用一半时间完成两倍工作？能，绝对能。但你必须非常努力地获得那些技能，而这些技能不是计算机科学学校会教的，也不常在你的第一份工作里有人示范。你必须下苦功，才能具备用一半时间完成两倍工作的能力。

在生成式 AI（GenAI）世界里，这一幕又在重演。人人都能成为程序员。是的，但不是人人都能成为同样水平的程序员。

**Gergely Orosz**

是的。这里似乎有一种模式：当一种新技术，或者像这次这样一种新方法论出现时，我想两者可以互换，它也是一种技术。一群受过高度训练的人能用它取得很好的结果。

然后他们把它发布出来，分享说，这对我们有效，这是结果。接着更大的行业围上来，说任何人都能得到这些结果，我们会把它卖给你、展示给你。

等你意识到不对时，比如一家大型银行发现它其实没那么管用，已经投入很深了。也许他们确实得到了一些小成果，只是不是同样的成果。

然后你可以说，这不就是蛇油的核心吗？蛇油确实有点作用，只是不是广告里宣称的作用。我们来谈谈 2001 年之后发生了什么。那时有一场很大的互联网泡沫破裂。

你能带我们回到当时吗？身处其中是什么感觉？那时候你在 Silicon Valley 吗？

**Kent Beck**

1987 到 1997 年，我们住在 Silicon Valley 上方的 Santa Cruz Mountains。那段时间大部分时候我通勤上班。然后我们搬到 Switzerland，1997 到 1999 年。

我们住在 Santa Cruz Mountains 的 Boulder Creek 后期，在 Southern Oregon、我祖母附近买了一块地。我们买了八公顷，全是树，然后开始开发供电、水井、道路等等。

后来去了 Switzerland。之前我们建了办公室，也有一辆拖车，然后去了 Switzerland，又回来。所以那个时候我住在 Southern Oregon 的乡下。

**Gergely Orosz**

整个行业刚经历了一场巨大的繁荣。我现在和做 AI 的人聊天时，觉得它和当下这波热潮有相似之处。然后突然崩盘。这个崩盘我也是从历史书或回看新闻里知道的，但据说非常突然，非常震撼。

我觉得这种风格里有一种学习元素，是无法复制的。所以当 Dario 说，我们要消灭软件工程时，你并不理解软件工程师到底在做什么。

我们会改变软件工程里的某些活动。这个我完全同意，而且我现在玩得很开心。但那种认为我们只是代码猴子，需求和什么指令进来，代码出去的想法，拜托。

**Gergely Orosz**

说实话，我确实感觉 Dario 对开发者，或者说软件工程师，有一种轻视。至少我从没看到任何迹象表明他喜欢他们，或者他曾经是其中一员。不，他显然不是。

**Kent Beck**

**Gergely Orosz**

顺便说一句，我们现在能不能谈谈这个？你在我们的讨论里已经多次提到这点。人们非常想替代我们这些开发者，我们也许应该稍微反思一下。

**Kent Beck**

你已经有时间反思了，为什么这个话题总是反复出现？

**Gergely Orosz**

因为我们有时候确实挺混蛋的。是的。

**Kent Beck**

这基本上就是全部原因。我的视角是：我是一个在谱系上的人，做了很久工程师，我父亲是工程师，我祖父按他那个无线电时代的方式来说也是个极客。所以我进入这个领域很自然。

我们不一定有很好的情绪调节能力，也不天然具备同理心。顺便说一句，这就是我打扑克的原因。当我没有很好地使用同理心时，我会得到反馈。

**Gergely Orosz**

我们往往比别人能轻松承受的程度更直接。是的，在商业环境里尤其如此。

**Kent Beck**

“我只是说实话”，或者“我只是问个问题”。这是我说过最糟糕的话。因为，好吧，你确实只是在问问题，但你问这个问题的方式很混蛋。我当时没有意识到，但我确实是，因为别人就是那样反应的。

所以我不期待任何人迁就我。有人会说，世界其他人应该适应我的古怪方式。并不是这样。我的意思是，那不会发生。

所以要学习同理心，学习读取肢体语言，学习听出语气。这些不是天生技能，但它们是技能，是可以学的。我永远不会像我的伴侣那样擅长，她是社交天才，但我至少可以在这些技能上不那么糟糕。

还有好斗这类东西。对像我这样的人来说，这是一种常见的社交策略，也曾是我的社交策略。我们之间有分歧，我解决它的方式是：这要多久？四周。必须两周做完。

当我说四周、你说不行必须两周时，那其实是在邀请一场对话。我不需要退缩说，哦，我会尽量完成。我也不需要说，去你的吧，混蛋。这两种回应都没有帮助。

更好的说法是：好吧，让我理解一下你的需求。这对我来说不是容易的任务，但我能做到。我有一个小清单。还记得第一部 Terminator 电影里，他有一个下拉菜单式的回应列表吗？

很多时候感觉就是那样。但拥有这些下拉菜单式回应，总比做出让对方疏远、并在谈话真正结束前就终止对话的事要好。

我认为正是这些事情要求我们学会用别人真的能听进去的方式沟通。所以我会从金融、体育、历史，以及我能找到的任何地方引入类比。

这是一种近乎拼命的尝试：理解别人，也帮助他们理解我的视角，以及我的视角能给这个情境带来什么，而且要用他们真正能理解的方式表达。

**Gergely Orosz**

跳到现在，这几年我们有了人工智能、大语言模型（Large Language Models, LLMs），不过现在我们就叫它 AI，或者按你的说法，叫精灵。

**Kent Beck**

它会满足愿望，但给你的并不真是你想要的东西。

**Gergely Orosz**

而且它有一些很有意思的特征。我想知道，你认为它会怎样改变个体开发者的工作？以及团队、公司、科技公司构建软件的方式？到目前为止你看到了什么？

我们已经谈了很多软件工程到底是什么，谈到了理解、沟通，以及在编码时学习。看起来这些东西即使没有被拿走，也肯定在缩小。

**Kent Beck**

那是一种选择，不过你先把问题问完。

**Gergely Orosz**

从整个行业来看，是的。而且我感觉这里有一个类比，就像你说接口刚出现时，人们过度使用接口。现在也像这样，我们有这些 AI agent，或者按我们的说法叫精灵，人们到处使用它，变得有点疯狂，忘掉了一些理性的东西。

**Kent Beck**

是的。这个问题可真开放。首先，开发速度确实加快了。我在想的一件事是，商业节奏并没有加快。这个错配会变得越来越明显。

我曾在一个客户那里，他们展示说自己每年在某个 SaaS 产品上花 200 万美元。有人用 vibe coding（Vibe Coding）做了一个替代品，对他们的用途更好，而且不用每年花 200 万美元。

那个供应商会怎么回应？在过去，也就是两年前，他们可能有好几年时间来反应。是的，我们有这个附加功能，每年收费 200 万美元，但人们并不真正喜欢它，最终他们会找到替代品。

他们以前也许有五年或三年来回应。现在则是：我们有这个附加功能，一直能收费，但它一个月后就会消失。

站在供应商一边，他们能不能也写出一个更好的替代品？可以，他们也能写出来。他们看到的加速和其他人一样。

但替代需求会不会经过客服、市场、销售、业务发展，再到产品组织？这条链路原本就是按五年设计的，而现在他们只有一个月，否则就会损失大块收入。

这不是 AI 的错。这只是加速，而他们的业务流程还没准备好及时响应。我个人对敏捷的定义是“及时响应”，而他们还没准备好应对新的速度。

就像你原本在开拖拉机，突然坐进了赛车。还是有轮子，还是有发动机，但你的技能准备好掌控那辆车了吗？问题不是它能跑多快，而是你能多快从 A 点到 B 点，穿过一条蜿蜒山路。

你习惯开拖拉机，现在却在 Ferrari 里。这不是车的错。但我预计这种趋势会持续展开，我们会看到一些公司失败，因为它们无法及时响应。

它们过去过得太舒服了，有点像有分类广告的报纸。再换个类比，分类广告曾经支付记者、纸张印刷，以及把印出来的报纸送到每家每户的成本。

然后分类广告消失了，新闻业必须回应。它在一些方面回应得不错，在另一些方面回应得很糟。相比这一切发生之前，我们从地方新闻中获得的服务变少了。

现在也一样，有些人一直依赖转换成本来保护利润，而转换成本突然降到了零。他们的利润也会降到零，有些人无法挺过这种变化，有些人可以。

另一面是，你正在为某项服务付费，然后想：啊，我可以用 vibe coding 做个更好的。于是你做了，但你只解决了问题的一小部分。那是冰山露出水面的部分。你能用 vibe coding 做出来的，是你看得见的那部分冰山。

我拿自己的经历来说。我在 Gusto 待了三年，它做小企业薪资。有人说，我只要问 Claude：我有这么多小时，时薪是这个，我在这个税档，我的工资支票应该是多少？它就把所有数字告诉我。我不再需要 Gusto 了。

**Gergely Orosz**

我当时就想，哦，你完全不知道这里面的复杂性。

**Kent Beck**

可以啊。你自己跑一个季度的薪资发放，然后再弄清楚要向不同州的各种税务机构提交哪些报表：我住在这个州，却在那个州工作，公司又设在另一个地方，那数字到底应该怎么算？

要正确、合规地执行薪资发放，里面有太多事情，并不只是总薪资和到手薪资。所以我们会看到有人闯进这些领域，然后说：我用 vibe coding 写出了冰山一角，把冰山剩下的部分都扔掉了。

然后我就出事了，因为我不知道接下来该怎么办。我碰到了这些下游问题，而我之前甚至不知道它们存在。

所以在那些认为 vibe coding 可以替代人的一边，我们会看到这种天真逐步显现出来。

**Gergely Orosz**

那软件工程师呢？很多工程师的身份认同来自能够精心写代码，关心这门手艺，能够在脑中想象许多东西，而这些工具在做其中很多事情上已经变得很强。

对于这些人，你会给什么建议？如果有这样一次新的技术变化，而你还想保持顶尖软件工程师的水平，可以做哪些活动，应该做出什么心态转变？

**Kent Beck**

我的励志格言是：没人知道。有人来问我，测试驱动开发（Test-Driven Development, TDD）在增强式编码的世界里怎么适用？我说，没人知道。不只是我不知道，而是没人知道。

我在 Facebook 学到的一个重要教训是，软件开发有三种不同的相态。第一种是探索阶段，你必须尝试许多不同的东西，因为你无法预测。

然后某个东西起飞了。我们已经聊过我职业生涯里的许多例子。火箭点燃以后，驾驭它上升的纪律，和探索空间的纪律非常不同；而探索本身也是一种纪律。

当你处在扩张时，你会非常专注地聚焦。它可能甚至是不可持续的，但不会持续很久。

之后还有一个阶段，你开始从中提取价值，用来供养下一组探索。

**Gergely Orosz**

这就是 3X，对吧？3X。探索、扩张、提取。这又是你在 2016、2017 年左右提出的一个模型？

**Kent Beck**

是的，2015、2016 年左右。我终于想明白了，我觉得自己理解了 Facebook 如何能同时做到规模庞大、持续增长并保持创新。

办法就是把处在不同阶段的项目，用完全不同的风格来对待。探索，就是你还只是在寻找某个东西，而且无法预测。

所以你必须尽可能多地尝试。这是一个数量游戏。你用最低成本，尝试尽可能多的互不相关的实验。

然后进入扩张。某个东西开始起飞，你就进入扩张阶段。你不再什么都试一点，而是聚焦在那个有效的东西上，丢掉其他一切，然后一个接一个地克服障碍。

等你达到一定规模，现在你可以预测增长了。你可以写出这样的计划：如果我们把产品推出到一个新国家，我们已经做过五个国家了，这里就是播放清单式的步骤。

**Gergely Orosz**

而且你知道该怎么做。那就是提取阶段。

**Kent Beck**

你已经达到了规模经济。你可以做小调整，却带来很大差异。你也有更长的生命周期。

所以在这三个阶段里，你怎么写代码、怎么管理项目、雇谁、雇多少人、组织结构是什么样，都完全不同。

过去 20 年，我们一直待在提取阶段。那里有一本玩法手册。它有些演化，但大体上存在。比如生产环境 bug 太多了，这里有三件可以尝试的事。

又比如，我们需要加快开发速度，这里有一些可做的事。人们有时不做那些事，但玩法手册是存在的。

成为资深工程师，意味着你知道这本手册。你知道得越多，就越有效。如果你还知道如何扩展后端，知道幂等性以及实现它会带来什么优势等等，你就更有用。

现在没人知道了。那本手册被擦干净了。那些把身份认同建立在“我知道手册”上的人，现在很害怕：那我是谁？

事实证明，编写一本玩法手册的技能，和应用一本玩法手册的技能完全不同。我们在对象时代做的那些事，就是在写手册。那是曲线里的探索部分。

并不是说没有手册时就无法高效，只是游戏变了。那些没有手册就感觉不安全的人，需要把脑子转过来：没人知道。

并不存在某本基于精灵（genie）的开发秘密手册，只要我付一百万美元就能拿到。它就是不存在。

当我们偶尔瞥见一点手册的影子，下周它又变了。对输入做很小的改变，可能导致输出发生很大的变化。

所以在这件事上，我们全都回到了探索姿态。我们能尝试的东西越多越好。

我会收到这样的问题：我觉得也许我们不该一次写一个测试，而应该一次写一堆测试。你觉得这样会有效吗？没人知道。试试看，然后告诉我们结果。

如果更多人在社区里尝试更多事情，并互相交流，比如我做了这件事，在这里加了这个 markdown 文件，产生了这个效果；另一个人说，我也加了，结果更糟。

那就要继续对话：你的情况有什么不同？正是这种对话，最终会产生玩法手册。

敏捷宣言（Agile Manifesto）是哪年？2002？对，2001 年。第一次 OOPSLA 是 1986 年。写出那份宣言花了 15 年。

所以我今天看到各种宣言时，我只会想：太早了。不是坏主意，我也很想有一份，只是太早了。

面向对象编程这个技术变化出现以后，过了 15 年，我们才能说出它的后果是什么，才能用简单方式表达如何有效使用这项我们日复一日用了 15 年的技术。

现在精灵出现了。人们问：新的宣言是什么？可现在还不是写宣言的时候。

**Gergely Orosz**

作为收尾，展望未来，AI agent、精灵、所有这些变化，以及我们所处的这种空白状态，哪些地方让你兴奋？什么给你能量？

**Kent Beck**

**Gergely Orosz**

**Gergely Orosz**

你整个职业生涯都体现了这一点，从非常早期的 TDD、极限编程（Extreme Programming, XP）、3X，到 Heidi First、Genie。

**Kent Beck**

是的，如果你看我的 GitHub，会看到 project、project two、project three、project four、new project、new project two、new project three、new project。

我不会试图微调。我会重新开始，然后说，好，如果我用不同顺序实现这些东西，如果我带着这个 markdown 文件实现，或者带着这个 commit hook 实现，会怎样？

我们作为一个群体，需要绝对什么都试。有些想法听起来会很蠢，却会产生很好的结果。有些听起来蠢的想法也会变成灾难。

但如果我们愿意从头再来，那就没关系。我们其实没有冒太大风险。

我可以找出答案。我坐下来，和精灵一起把它做出来。然后就有了一个以前不存在、现在存在的东西，因为我的想象力和工作而存在。

我曾经受够了编程里那些愚蠢的细枝末节。比如，为了那个东西你需要升级到 7.1 版本，然后又导致别的东西坏掉，接着又让另一个东西坏掉。

这意味着我不能用 7.1 版本，我必须……我真的讨厌这种事。你有了一个想法，投入感情，做到一半，却发现因为毫无道理的原因做不下去。

我讨厌那种感觉。而现在，这类阻塞基本不会发生在我身上了。所以这简直太舒服了。

我有 40 年积累下来的想法：这个会很酷，可它太大了。现在这些想法突然又重新回到了牌桌上。

**Gergely Orosz**

敏捷宣言是在做了 15 年面向对象编程之后，Kent 这样的人才得以总结出经验。对于 AI，事情仍在快速变化，而 Kent 很诚实地说：现在，没人知道什么真正有效。
