与 Hillel Wayne 的形式化方法访谈

本期节目聚焦“AI 时代软件工程是否还需要形式化验证”这一核心问题，由 Gergely Orosz 邀请 Hillel Wayne 深入讨论。他首先回顾了自己从软件工程入门到推动形式化方法研究的经历，并结合 Crossover Project 的背景说明软件是否属于传统工程的争议。对话随后进入实践层面：如何从规格说明进入证明、形式化方法在实际项目里的可行边界、以及与属性测试、测试驱动思路的关系。Hillel 讨论了工具在不同规模项目中的应用现实，并提到并发与分布式系统场景对可靠性要求更高、也更容易暴露验证难题。节目也分析了 AI 生成代码后，验证负担是否会下降或上升，以及开发者如何更务实地在高价值环节使用形式化技术。最终两位认为，形式化验证并不是唯一答案，但在关键系统里是重要补充，关键在于平衡投入与风险。

播客

主持人和嘉宾

主持人

Gergely Orosz

The Pragmatic Engineer Podcast 的主持人，长期关注软件工程实践与工程文化。

嘉宾

Hillel Wayne

软件工程师与作者，专注于形式化方法、编程语言与系统可靠性研究，并发起 Crossover Project。

AI 与形式化验证的争论

Gergely Orosz

最近大家常说，AI 要大规模写代码后，人类需要数学证明来保证程序正确，所以形式化验证会不会因此成为主流？这正是今天讨论的核心，也是节目安排的起点。

我们今天请来的嘉宾是 Hillel Wayne。很多人都知道他在形式化方法、逻辑和 TLA+ 上的工作。先抛个大问题：AI 生成代码后，真正可靠的程序要如何验证？

软件是否是工程：Crossover Project 的起点

Hillel Wayne

我从小接触电脑，大学里也做过一点编程。起初我更想做物理和数学，梦想是研究宇宙的‘心跳’，但后来发现自己更喜欢实验室里的编程。于是我离开学校，去旧金山做 Ruby on Rails，也从教育科技开始。

后来在另一份教育科技工作里，我渐渐转向了形式化验证和形式化方法。你问我最近的项目时，我会讲 Crossover Project：我采访了十五到二十位不同工程领域的人，想回答‘软件工程算不算工程’这个问题。

Gergely Orosz

这也是一件非常有意思的事。很多开发者在讨论里会分成两派：有人觉得我们不算工程，有人觉得软件是最特殊、最有创造力的工种。你最开始站在哪一边？

Hillel Wayne

我起步时非常偏向‘我们不是工程师’。后来读了大量工程书、软件文章后，发现两边其实比想象中更接近。真正把软件放在工程语境里看后，我意识到自己可能错了：软件也有许多与传统工程一致的核心问题。

Gergely Orosz

你后来是怎么做的？你是怎么把整个传统工程领域都走一遍去对比的？

Hillel Wayne

我至少覆盖了十五到二十位受访者，横跨六七个领域。目标是把桥梁、芯片、化工、工业工程、机器制造这类不同材料和流程都放到同一框架里比较，看看软件工程的共性与边界。

Gergely Orosz

对你来说，最醒目的共同点是什么？

Hillel Wayne

一个共识是：几乎所有工程都在工程误差的代价和迭代速度之间拉扯。传统工程里成本高、试错贵，就必须更谨慎；软件通常成本低、迭代快，就更适合频繁修正。

Gergely Orosz

我听到的另一个点是传统工程也有很多层级，而且不是单一模式，像烟测、建模、样机、现场试验等。你觉得这个“层次”对软件有什么映射？

Hillel Wayne

软件的特点是迭代更快，但这不意味着它缺少工程含义。比如化学实验次日出结果、土木工程难以反复试错，但软件可以在秒级重复。再比如我们测试 CPU 排列时，软件输出几乎不受环境波动影响，属于“可复制性”很强的系统。

Gergely Orosz

所以软件不需要承受大量物理噪声，变成了更一致的对象；但也因此会误判一些工程现实中的变化。你后来补充的一个对比是客户接触和开源文化吧？

Hillel Wayne

对。传统工程里不一定每个人都和终端用户常接触，但软件行业经常离不开用户反馈。另一个关键差异是，软件更容易共享知识：语言、框架、库、课程都在线公开，开源成为默认行为，学习门槛反而更低。

Gergely Orosz

这也是为什么今天的会议和社区生态更重视实践者交流，不只是科研发表或单纯卖产品。我也观察到很多大公司也不太会把全部实现细节完全保密。

Hillel Wayne

我猜想，除了文化，另一个原因是软件和产品材质是同一类材料。我们用软件去写软件，反馈闭环更紧。和用刀具、机床、PCB 去做实体产品不同，知识复用难度更低，所以共享更容易发生。

Gergely Orosz

你还提到版本控制。对比传统工程后你感觉这件事最震撼？

Hillel Wayne

我采访的大多数工程同学都说，版本控制是他们很想要却没普遍落地的能力。软件里我们从一开始就有几乎现代级别的版本控制生态，不只是变更管理，而是协作、回溯、分支和审计都天然配套。

至于“工程师身份”这个问题，我现在基本会回答‘我们是工程师’。我在写 Crossover Project 前是怀疑的，但这次调研后，至少在我看来软件工程师与传统工程师是同一条连续谱上的。

形式化方法入门：从规格到证明

Gergely Orosz

那我们从你的角度讲讲形式化方法吧。对很多不熟悉的人，形式化方法到底是什么？它和平常写测试、做代码评审到底差在哪？

Hillel Wayne

举个最简单例子：求列表最大值。如果你问的是 max 的定义，最直观答案可能是‘返回列表里最大的元素’。形式化方法会把这个隐含知识变成可检查的规格：对每个输入列表，输出必须属于列表且不小于任意其他元素。

定义完规格后，下一步就是检查你的实现是否满足它。测试只是抽样检查少量输入；类型系统也能检查一类结构性约束；形式化方法追求的是通过数学证明覆盖全部可能输入。

Gergely Orosz

这听起来像是高级数学证明课。和大学里那种代数变换证明方程很像，都是一步步把复杂问题转成可验证的形式。

Hillel Wayne

对，差别在于这类证明多数会被工具自动化。你给它初始假设和目标结论，工具通过推理自动寻找中间步骤，像数学家手工演算但规模更大、速度更快，当然也会向你反馈‘需要再补一个引理’。

Gergely Orosz

问题也很现实：明知道形式化很强，那为什么现在不是每个系统都在用？是不是复杂度太高？

Hillel Wayne

是的。很多真实任务需要先完整建模现实世界。比如写一个‘找出目录里最长文件’的函数，文件系统里有权限、符号链接、目录循环、二进制文件编码等边界，规格本身就会膨胀得很快。

如果你只需要 99% 的情况正确，工程师通常会写一些‘足够好’的实现。再追求 100% 时，代价通常不成比例，所以形式化验证并不适合所有问题。

Gergely Orosz

那它什么时候会有价值？

Hillel Wayne

我会分三类：一类是系统级错误后果巨大、必须严格保证的，比如某些安全关键领域；二类是关键子系统，比如数据库内核、加密原语；三类是把现实世界先抽象成模型验证，再把洞补回主系统。

Gergely Orosz

你的真实工作里也有这样的例子吗？比如系统内核、固件、训练平台这类。

Hillel Wayne

有。比如我做过固件、列车信号收发器的验证，主要目的是提前发现‘逻辑上不该发生’的状态。另一类是数据库、分布式系统里的核心模块，先把关键行为模型化再验证。

形式化工具与实践场景

Gergely Orosz

很多听众会马上追问：有哪些工具在行业里真的能用？我想直接听你给一个实战视角。

Hillel Wayne

TLA+ 是我讲得最多的。它擅长描述离散、并发和交织行为的系统。你可以把状态机写成规范，再用模型检查器遍历状态空间，找出违反不变量的反例。

例如我做了一个交易平台玩具模型：三个人交换商品、挂单、接受/拒绝。我们设了‘所有权变更必须有对应提议并被接受’的约束，模型很快暴露出一种交错导致权属错误转移的路径。

这个反例非常有意义。模型会生成 Alice、Bob、Carol 的一条状态序列，暴露你肉眼容易忽略的并发时序问题。人类要找到这条路径很费力，但模型检索只要几秒就能给出。

你会看到状态图通常很大，可能是百万级到亿级状态，因此更多时候它用于演示和局部验证。对全量系统，工程上仍然是‘抽象得好坏决定了价值’，不是盲目建成巨大模型。

Gergely Orosz

我记得你提到过 AWS 的公开案例。那类大规模公司采用形式化方法后，通常能挖出多轮才出现的深层 bug。

Hillel Wayne

对，像 AWS 论文里有多层系统里罕见的长链路错误。它的价值不一定在于天天上新 bug，而是把某类错漏提前显性化，减少长期事故。

Gergely Orosz

除了 TLA+，你还会推荐 Alloy、P 或者 Prism 吗？我想听一条清晰的工具谱系。

Hillel Wayne

我会把它们放成梯度：Alloy 适合静态模型和关系约束，快而直观，而且可视化；P 更偏向系统状态机交互；Prism 这类工具可以做概率性分析，但门槛更高、更偏学术。

如果你做的是验证某段代码而不是抽象模型，还会看到 Dafny、K、Event-B、Model Checking for Java/C/C++ 等体系化路径。核心仍然是‘不同工具偏向不同问题域，不存在万能刀’.

属性测试与形式化验证的关系

Gergely Orosz

我们再说一个听众熟悉的概念：property-based testing。很多人会把它当成更高级测试框架。和形式化验证到底差在哪里？

Hillel Wayne

我会继续用 max 的例子。若你写过一个坏实现，比如只看前3项，它可能只在某个很小的反例中出错。性质测试不会证明‘所有输入都对’，但可以生成很多随机和极小反例来快速击穿错误。

它通常会先用大量样例找失败，再缩小为最小反例，给你可理解、可复现的失败输入。相比形式化，这不是完整证明，但更容易上手、成本更低，适合更广泛团队。

Gergely Orosz

也就是说，很多团队可以用性质测试作为入门，再逐步决定是否值得上 TLA+ 或 Alloy。

Hillel Wayne

是的。我的经验是，形式化不是替代测试，而是把测试的‘抽样验证’和‘系统级数学验证’连接在一条连续线上。不同问题选不同预算。

AI 时代的验证新现实

Gergely Orosz

现在很多团队都说 AI 写更多代码后，需求更高。你看到的实际趋势如何？会不会更容易推动这种验证文化？

Hillel Wayne

我确实看到更多人找我帮他们用 AI 写规格、做检查和回归。特别是一些 LLM 平台会把‘生成属性测试’做得很好，减少手工样板。业务上也有很多人开始把规范、测试、验证放进流程。

但 AI 最擅长的仍是写语法和解释报错，不擅长的是‘提出一套本质性的规约属性’。它很容易给出像‘P 或非 P’这类总为真命题，听起来像完成了证明，实际上没约束系统行为。

我也见到有人尝试直接让 LLM 生成完整规范，但质量参差。对长生命周期、复杂业务语义的约束，模型往往给出模板化正确性定义，真正关键的“做什么才算成功”仍然要人来定义。

Gergely Orosz

你能给一组你自己会用的实操建议吗？对软件工程师尤其是分布式系统工程师。

Hillel Wayne

我会先回到基础：培养对数学的基本直觉，尤其是离散数学、逻辑和图论。再配合对关键流程的抽象能力。并发系统里，最核心的是‘哪些前提下状态转移是非法的’，把它们写进属性。

如果你是新手，先从‘轻量规范 + 属性测试’起步；当你发现某类错误代价很高，比如跨机房一致性、授权、竞态、资金流等，再上形式化工具。别一上来就用最重的方案。

分布式系统中的并发与职业焦虑

Gergely Orosz

我们再回到分布式系统。你经常说并发难的根因是我们缺乏练习，也不是天生‘不擅长并发思维’。这和程序员真实工作中的迁移、重构很像。

Hillel Wayne

完全一致。做过少量竞态修复的人很难快速识别更多竞态。形式化工具的价值之一是把这种训练压缩：你改一个模型就能在几秒拿到新反例，而不是花数周线上验证。

Gergely Orosz

这与付费能力、市场规模变化一起看会不会改变职业结构？

Hillel Wayne

我一年前写的观点里认为，大规模低成本自动化可能让‘纯写代码’岗位变化很快。AI 能放大经验丰富者，但不会让深层理解消失。它更可能让一线工作分化：普通实现工变少，少数高质量工程师更稀缺。

我担心的是软件工程师的工作特权被磨平，比如更易上手、也更容易被白领化标准化。也可能出现少数高薪岗位更稀缺、竞争更激烈、门槛更高的未来。

Gergely Orosz

这听起来像在回到保险、银行交易系统那种职业老化曲线。短期可见的变化是哪些？

Hillel Wayne

你会看到招聘结构变化：对分布式、数据库、基础能力要求更突出，某些岗位更偏自动化；而很多‘纯战术编码’型岗位可能更多被 AI 辅助。长期看，软件开发不会消失，但组织对深度能力的要求会升高。

Gergely Orosz

也许更重要的是你最后仍然表达的乐观：AI 不是替代全部。哪怕在支付、交易、竞态这类高风险场景，经验与判断还没法完全消失。

Hillel Wayne

是的。更现实的预期是：未来十年我们会看到软件工作更偏向专业化，和一年前相比，底层技能和设计能力仍然决定上限。自动化会普及，但不会消灭‘懂系统的人’。

收束与建议

Gergely Orosz

如果把今天对话收束一下，你会如何给工程师建议：哪些工具和阅读最值得？

Hillel Wayne

我会推荐从工程思维和系统安全入手，先读《Engineering a Safer World》，理解事故为什么发生、如何建模风险。其次是《Data and Reality》重新思考数据和身份，再配合《Debugging: The Nine Simple Rules》建立调试纪律。

Gergely Orosz

你也提到过数学和逻辑能让团队在系统层次上更稳。对于想进入分布式系统的人，这个建议非常具体：先学会描述问题，再决定是否需要形式化。

Hillel Wayne

我还会再重复一次：形式化方法不是炫技，而是‘把假设讲清楚’。你的程序正确性不是一句‘它跑过了测试’，而是‘在明确假设下我们知道它不会违反关键性质’。

当你把这一层做好后，AI 能更好地帮你做语法修正和样例生成，但真正关键的设计空间边界，还是人要定义。今天这个讨论不算完结，只是把‘不动脑’的问题替换成了‘更系统地想清楚’。

Gergely Orosz

也感谢你分享了这么细的拆解。最后一句，如果让你给一句话概括：形式化验证会不会在 AI 时代普及？

Hillel Wayne

我会说它会更常见，但不会全民普及。它是少数高价值场景的放大镜，而不是每个项目都要套的‘全量流程’。
